# 历史凭据检测结果复用实验（2026-10-17）

提交基线为 `57711d2`（`fix: unify credential detection, protection, and audit evidence`）。本目录记录后续独立实验，缓存只通过 test-support 构建的 `CABLETIDY_TEST_CREDENTIAL_CACHE=1` 开启。普通构建继续使用完整检测流程。

PR 分支已 rebase 至 `origin/main` 的 `d5e369a`（0.5.0-rc.2），原基线提交对应 `6add8ea`；`git range-diff` 确认检测修复和缓存实验补丁内容保持一致。以下性能数值与二进制校验和来自 rebase 前的 0.5.0-rc.1 构建，未将发布元数据更新后的新二进制冒充为原始测量对象。重新运行可使用 PR 中的 `6add8ea` 构建等价检测基线，输出校验和与分位数将重新生成。

## 实验实现

采用确认过的流程：复用兼容旧内容的检测事实 → 检测新增／变化内容 → 用新增可信值复查历史 → 为当前原文生成候选和执行保护。

缓存由运行时保护会话持有，与会话空闲 TTL 一起释放。TTL 未过期只表示缓存可以被查询，不能证明内容仍可复用。复用键包含检测版本、解析路径、字段、节点类型、继承的凭据／Schema／tools／immutable／opaque 语义及完整解码文本的 SHA-256。当前位置索引改变会保守失效，因此首版适合原有索引保持不变的历史追加；它不沿用页面“历史”标签或将共享会话头推断为同一次历史事件。

缓存保存候选提取模板，包括完整检查后的零命中结果。当前 JSON 每次仍完整解析，原始字符串拼写与字节范围重新映射，候选／快照 ID 重新生成。`type: thinking` 出现在内容之后时，仍根据当前对象结构补做不可替换判断。实际 `replaced`／`not_replaced`、替换后的正文和转发状态不进入缓存；审计与保护继续共享当前请求冻结的同一份 `Detection`。

可信目录完全相同时直接复用。目录只有新增条目时，检查旧文本是否包含新增值：不存在且没有反斜杠时复用；可能出现新增值或存在转义时，完整重检该字符串，保留重叠范围与来源处理。目录删除、证据／类别／匹配策略变化时完整重检。任何解析失败、目录不完整或资源不足都不发布本轮缓存。

每会话缓存上限 4 MiB／1,024 条，计入候选和去重后的目录快照保留内存；触顶清空后继续检测。请求内待发布缓存另有相同上限，临时目录与所有保留内存受已有 256 MiB 全局预算约束。目录快照复用 `Arc`，不逐请求无界复制。缓存包含已发现凭据的内存副本，生命周期受会话和预算约束，不落盘。运行时映射的旧版本仍只用于还原。

本次另将原始 JSON 字符串拼写的读取延后到确有候选时，避免零命中字段重复读取；该优化也作用于缓存关闭组。缓存关闭时不计算内容哈希。

## 验证与性能方法

新增 Rust 回归比较缓存与完整检测的所有候选事实（只忽略本轮生成的 ID），包括原文字节范围、解码范围、来源、类别、匹配策略、角色、结构拒绝及目录摘要。覆盖 Unicode／原始拼写变化、重复键、嵌套转义、新凭据影响旧文本、无关目录增加、策略／目录失效、结构迁移、对象后置 opaque 类型、失败不发布、内存上限与淘汰、会话隔离／空闲过期和当前实际替换。

HTTP 多轮用例确认旧文本从未检出变成实际替换，后续继续复用，响应恢复 A，审计与保护引用同一新候选 ID／位置／状态，独立会话不继承旧学习值。已有 JSON、SSE、工具参数、结构拒绝及错误路径在缓存开启条件下回归。

最终 `npm test` 全部通过：161 项 Rust、648 项主要 JS 集成、13 项启动、3 项开发测试。缓存开启的既有 108 项凭据保护专项通过；新增多轮 HTTP 用例最初因断言误把解析位置当作字段路径而失败，修正断言后单独通过，并在最终全量测试中再次通过。缓存开启的主合成集合 **672/672**、多轮／结构契约 **100/100** 通过，812 条审计记录均完成；完整回放与冻结 manifest 见 [regression.json](regression.json) 和 [regression-manifest.json](regression-manifest.json)。这些是既有语料的回归，不能作为新的独立留出证据。`cargo fmt --check`、`git diff --check`、脚本语法检查和 `cargo clippy --locked --all-targets --features test-support -- -D warnings` 均通过。

[benchmark.mjs](benchmark.mjs) 配对比较四组：提交版本、实验缓存关闭、实验缓存开启、实验保护关闭（审计保持开启）。每组同工具链 release／thin LTO，使用同一批合成载荷和本地模拟上游；每场景独立预热，再测 8 组独立会话，每组 4 轮增长到目标历史大小、4 轮追加。每轮交替组顺序，等待审计完成；测量时不并行执行构建或测试。

主分位数只统计历史已增长至目标大小后的 32 个请求（单并发）或 128 个请求（4 并发）。同时保留全部增长过程、检测耗时、复用／失效计数、批次审计完成时间和资源样本。上游逐字节比较整个 JSON，仅规范化随机占位符，响应文本必须恢复为原值。模拟上游收齐字节后统一解码 UTF-8，避免 HTTP 分块边界损坏 Unicode。

`work` 计数合计检测内部两遍，包括 JSON 键字符串，不能解释为唯一历史消息数量。`reusedDecodedBytes` 同样可能累计两遍，不等于少解析了同样大小的 HTTP 正文。检测计时包含解析、哈希、目录检查和当前候选位置重建，不能视为纯正则执行时间。

## 适用边界

缓存减少重复候选提取与目录全量匹配，不跳过完整原文解析／哈希、当前位置重建、A→B 执行、出站验证和 B→A 还原。带转义的历史在目录变化时保守重检，频繁改写的内容会失去大部分跨请求命中收益；同一请求内部第二遍仍可能复用。会话注册表仍串行持有互斥锁，尚未处理大并发下的锁争用。

本地合成结果不能证明生产性能、≥99% 精确率、独立来源语料门槛或 1.2 倍发布目标已达成。

## 配对结果与建议

完整结果、二进制校验和、工具链及逐请求数据见 [performance.json](performance.json)。共 2,464 次模拟上游调用（含种子目录与预热），2048 次测量请求；HTTP 错误、完整出站载荷差异及响应还原错误均为 0。

| 场景／正文／目录／并发 | 提交版本请求 p95 | 缓存关闭 p95 | 缓存开启 p95 | 相对提交下降 | 检测 p95：关闭 → 开启 |
| --- | --- | --- | --- | --- | --- |
| 稳定／64 KiB／32／1 | 101.57 ms | 99.75 ms | 73.06 ms | 28.1% | 31.76 → 7.26 ms |
| 稳定／256 KiB／128／4 | 428.87 ms | 431.95 ms | 218.72 ms | 49.0% | 95.63 → 26.24 ms |
| 每轮新增无关凭据／256 KiB／32／1 | 129.10 ms | 145.33 ms | 98.19 ms | 23.9% | 81.27 → 25.22 ms |
| 第五轮凭据影响旧内容／64 KiB／32／1 | 96.14 ms | 101.93 ms | 73.51 ms | 23.5% | 33.58 → 10.28 ms |
| 每轮改写首个历史块／256 KiB／32／1 | 131.01 ms | 140.41 ms | 101.79 ms | 22.3% | 78.19 → 36.28 ms |

同一实验二进制缓存开启相对关闭，请求 p95 下降 26.8%–49.4%，检测 p95 下降 53.6%–77.1%。公共读取优化的 p95 比提交版本约为 0.98–1.13，单独没有可靠改善证据，不能把缓存收益归给读取优化。样本来自 8 组相关的增长轨迹；p95/p99 是描述性分位数，未估算独立生产置信区间。

稳定历史每请求两遍合计完整提取由 80–104 个字符串降为 5 个；目录每轮增加时为 7 个。第五轮新增值影响历史时确实有 2 个缓存节点失效，提取量增至 10 个，后续恢复复用；整份规范化出站 JSON 仍与独立预期一致。改写首块时每轮提取 6 个，其余块保留复用，因此该场景仍改善，不能外推到所有历史块同时被改写。

缓存开启组的批次审计完成 p95 为 139.49 / 523.96 / 318.31 / 141.65 / 320.04 ms，顺序同上表；该值包括整个批次和轮询，不能视为单候选审计时延。每会话缓存保留量观测 p95 为约 78 / 253 / 218 / 97 / 87 KiB。采样在批次后进行，观测到的工作内存以会话缓存为主，不能代表转换中的瞬时峰值；最大批次样本约 12.0 MiB，最大进程 VmHWM 约 59.4 MiB。全局工作内存／加密暂存预算仍为 256／512 MiB。

缓存保护相对保护关闭的请求 p95 比为 0.88 / **1.52** / 0.86 / 0.86 / 0.99。关闭保护组仍同步执行完整检测供审计使用，而且不保留保护会话学习目录；单并发下可能比复用检测的开启组更慢，不能解释为保护本身没有成本。256 KiB、4 并发仍超过 **1.2 倍门槛**，本次不能宣称已解决全部延迟问题。

建议继续沿此流程开发正式缓存，同时补测真实长会话、带大量转义的工具结果、目录频繁变化、整段历史改写和更多并发。下一步应拆分并定位会话锁等待、位置重建、转换／验证、回包还原及后台审计开销；保护关闭路径也可复用相同检测事实缓存，但需独立设计其会话生命周期，不能因性能测量而临时改变开关语义。完成这些验证后再决定默认启用。当前实验开关保持测试构建专用。
