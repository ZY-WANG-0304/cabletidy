# 第三阶段验收记录（2026-10-17）

审计与保护的展示、版本迁移和复用契约已完成开发及回归。离线评估暴露并修复了类型注解字面量和 `session_token` Cookie 漏检。发布门槛尚未全部达标：当前语料以合成模板变体为主，不能算作 600 个独立来源标注；保护开关的 p95 延迟比也超过提案 1.2 倍目标。未进行生产灰度、重启已安装实例或部署。

## 检测事实、审计判断和实际动作

检测规则为 `credentials-4`，每个请求仍冻结一份 `Detection`，审计与保护共享候选 ID、类别、来源、证据和原文字节位置。内部两遍扫描属于一次检测，不是两个消费者各自扫描。

审计策略独立记录 `audit-4`，风险规则／缓存依赖为版本 4。强证据产生 `credential_warning`（凭据告警），低置信度产生 `candidate_notice`（候选提示）。判断依据分别解释本地已知值、明确凭据值上下文、支持格式／私钥封装、未确认候选。高置信度表示离线检测证据充分，不表示验证了 Key 活性或账号可用性。

保护策略保持 `protection-2`。`replaced` / `not_replaced` 完全按执行记录显示；低置信度不覆盖实际状态。未替换原因包括策略未选择、保护关闭、结构无法安全替换或执行失败，请求转发结果单独记录。响应检测事实不虚构请求替换状态。风险页展示来源、类别、候选提示／凭据告警和已记录的执行状态；保护页展示候选总量、低置信数量和未替换原因。缺少旧证据时显示未记录，避免将未知算作未替换。

升级规则后，旧检测版本映射只用于当前会话 B→A 还原，不能用于新请求识别或 A→B 复用；强 A 重新检出时生成当前版本 B。活跃旧请求继续持有原映射。历史审计原有版本、置信度、证据与结论保持不变，计算缓存按版本失效。运行时映射仍不从审计数据库自动恢复。

## 同硬件性能校准

第二阶段基线在第三阶段修改前复制完整未提交源码，使用同一 Cargo.lock、Rust 工具链和 release／thin LTO 配置分别编译。版本 2 的基线不是仓库 HEAD，因为此前阶段仍未提交。固定快照的构建输入校验和见 [stage2-benchmark-source-manifest.json](stage2-benchmark-source-manifest.json)，二进制校验和、CPU 和工具链见 [性能报告](stage3-performance.json)。模拟上游本地响应，审计始终开启；每场景四次预热、32 轮交替配对批次，每轮等待该批审计完成。

| 正文目标／现有映射／并发 | 样本数（每开关组合） | 第二阶段保护 p95 | 第三阶段关闭 p50/p95/p99 | 第三阶段保护 p50/p95/p99 | 第三／第二阶段保护 p95 |
| --- | --- | --- | --- | --- | --- |
| 4 KiB／0／1 | 32 | 53.02 ms | 5.96 / 8.39 / 8.83 ms | 50.49 / 54.07 / 58.26 ms | 1.02 倍 |
| 64 KiB／32／4 | 128 | 162.09 ms | 40.97 / 47.35 / 77.43 ms | 97.70 / 163.58 / 175.75 ms | 1.01 倍 |
| 256 KiB／128／8 | 256 | 903.47 ms | 134.62 / 157.83 / 176.16 ms | 491.34 / 897.19 / 926.18 ms | 0.99 倍 |

第三阶段保护批次审计完成 p95 为 65.73 / 250.51 / 1,112.26 ms，包括整个并发批次和 5 ms 轮询分辨率，不能当作单请求审计延迟。全部组合错误率 0；工作内存仍为 256 MiB、加密暂存仍为 512 MiB。第三阶段保护进程 VmHWM 为约 17.0 / 33.1 / 47.4 MiB（包括启动、预热和测量的进程高水位）。保留计量每 20 ms 采样，保护组合观测到的工作内存峰值约 1.35 / 9.41 / 16.61 MiB，加密暂存约 8.01 KiB / 319.93 KiB / 2.25 MiB。采样可能漏掉短峰值，不能等同精确资源峰值；低样本 p99 只作描述。

保护开启／关闭 p95 比分别为 **6.44 / 3.45 / 5.68 倍**，**未满足提案中的 1.2 倍门槛**。第三阶段相对第二阶段未出现明显增量延迟，但这不等于整个保护链路已达标。正文识别、多个字节／结构验证、会话映射和回包还原的同步成本需要独立分段测量，当前不能把总开销归因于某一段。

检查发现编辑读取器会在字段边界返回很小的块，已在 HTTP 前用固定 32 KiB 页合并本地读取，字节完整性测试通过；复测没有显示保护链路有实质延迟改善，不能将其宣称为性能问题的根因修复。改动前结果见 [stage3-performance-before-buffering.json](stage3-performance-before-buffering.json)。下一项性能工作应记录阶段耗时与真实候选／映射规模，再优化重复目录遍历、位置翻译或校验流程，不削弱检出、拒绝与出站验证。

复现：分别构建基线和当前 `cabletidy-test-daemon` release 二进制，将 `CABLETIDY_BASELINE_BINARY` 指向基线后运行 [benchmark-stage3.mjs](benchmark-stage3.mjs)。研究输出默认为忽略目录 `.cabletidy-debug/credential-protection-evaluation`。不同时运行全量测试或其他高负载任务，以减少延迟干扰。

## 工程验证与发布边界

`npm test`：152 项 Rust、647 项主要 JS 集成、13 项启动、3 项开发测试全部通过。新增测试验证同候选事实与实际状态、保护关闭审计、并发快照隔离、旧检测映射还原专用、活跃旧请求、历史策略不重写、类型注解字面量、Cookie 与本地页读取完整性。已有 JSON／SSE／嵌套编码、资源预算和错误路径回归继续通过。

`cargo fmt --check`、`git diff --check` 和 `cargo clippy --locked --all-targets --features test-support -- -D warnings` 通过。Playwright 桌面／手机检查通过，新增低置信候选提示、结构内强凭据未替换、保护关闭、实际状态与无横向溢出；截图位于忽略目录 `.cabletidy-debug/credential-protection`。

发布前仍需要：足够独立来源的标注与留出集、性能门槛处理，以及授权真实业务灰度。产品目前没有审计关闭开关，保护核心的独立调用在 Rust 测试中验证；不能声称完成了不存在的“审计单独关闭”配置验收。多语言复杂语法／转义、任意编码、自定义 Cookie 语义、私钥结构及活性验证等既有边界仍需保留。
