# CableTidy 供应商、模型与 Cable 重构设计

日期：2026-10-19。状态：已确认首批 A+B，实施中；真实供给验证按确认的分工完成。

## 1. 目标与范围

**供应商管理模型供给事实；Cable 选择供给和客户端提示词策略；客户端适配由代码实现。**

- 一条 Cable 对应一种客户端；同一种客户端可以创建多条 Cable。
- 一条 Cable 可以选择多个供应商，并显式勾选各供应商的部分模型。添加供应商、发现模型或同步目录都不会自动把全部模型加入 Cable。
- 供应商是服务实例，不限定类型；同一实例可以提供多个协议接口及不同类型的模型。新建时填写名称，通过接口和模型列表添加多项资源，确认后一次性创建；详情继续独立管理各项资源。
- 模型适配纳入本次重构：代码根据客户端及版本、接口协议、实际模型身份或类型和能力，执行内置参数映射、工具转换、模型定义生成与历史处理规则。同一种已支持组合可用于多家供应商实例。不提供通用的用户自定义适配或映射编辑器。
- 原“适配预设”收紧为 **客户端提示词策略**：Cable 选择默认或可选的内置模板。模板与工具约定由代码配套维护，选择粒度遵守客户端实际机制。
- 首期已确认选择第 6.1 节的 A+B：Codex × Responses 下的原生 GPT 类型及指定的六个非原生目标模型。B 已扩展为一组模型，不再限定为一个非原生模型类型；按各模型身份和能力分别实现、验证，不假设六者共用同一适配规则。供应商实例数量不受此限制，验证接口后续确定；其他组合不属于首期验收要求。
- 供应商预设仅是预填配置的辅助，不是适配前提，不进入首期数据依赖、页面流程或验收。
- 跨协议转换、多供应商自动路由、负载均衡和故障切换属于本设计，按实现与验证结果逐项开放。基础阶段已支持一条 Cable 使用多家供应商；每个请求通过所选客户端模型确定来源，无需等待自动路由。

多条 Cable 的服务和配置独立保存。应用到同一份客户端配置时管理当前激活线路和共享字段；这不限制 Cable 的创建数量，也不影响其他线路的本地服务。

## 2. 调研依据与设计结论

| 调研结果 | 本设计采用的规则 |
| --- | --- |
| Codex 自定义模型名需要完整目录，目录提供指令、reasoning、上下文和工具元数据 [1] | 代码生成与客户端模型 ID 匹配的完整定义，模型改名不等于完成适配 |
| Claude Code、Gemini CLI、不同版本 OpenCode 的提示词和能力配置机制不同 [2][3][4] | 适配按客户端及版本实现；无法逐模型配置的字段不能伪装成逐模型生效 |
| Magpie 显式成员与目录匹配成员分开，并维护会话/工具回合亲和 [5] | Cable 使用显式模型选择；自动路由只在用户配置的候选来源内执行 |
| OpenCodex Combo 聚合能力和窗口，且对流式输出提交边界作判断 [6] | 多来源共享客户端模型时声明共同能力；故障切换不能拼接不同来源的回答 |
| Magpie 通过代码处理协议和模型差异；OpenCodex 维护能力及内置适配器，并提供有限配置映射 [5][6] | CableTidy 首期采用内置规则，用户配置集中在供给事实、模型选择和提示词策略，不建设通用适配平台 |

当前 CableTidy 的运行路径要求每条 Route 只有一个上游，模型设置主要属于 Virtual Provider。本次需要同时调整模型归属、请求选源和客户端配置生成，不能只修改页面的供应商选择框。

## 3. 数据归属与关系

| 对象 | 归属 | 核心内容 |
| --- | --- | --- |
| 供应商 | 全局管理 | 系统生成的稳定内部 ID、名称、启停状态；所属接口和供应商模型记录，不设供应商类型 |
| 接口 | 供应商内部 | 系统生成的稳定内部 ID、名称、协议、地址、内置认证方式与凭据引用；多个接口可引用同一凭据 |
| 供应商模型记录 | 供应商内部 | 以“供应商 ID＋上游模型 ID”为唯一键，无独立内部记录 ID；实际模型身份及版本或未知、可访问接口引用、能力和限制及必要的接口差异 |
| 客户端适配实现 | 代码维护 | 支持的客户端及版本、协议、模型类型组合；依据实际模型身份与能力执行内置参数映射、工具转换、模型目录生成、历史处理，记录实现版本 |
| 客户端提示词模板 | 代码内置 | 适用客户端及版本、模型条件、原生或兼容指令、配套工具约定、生效范围和模板版本 |
| Cable | 线路管理 | 客户端类型、供应商引用列表、本地地址、模型绑定、默认模型、客户端提示词策略与启动设置 |
| Cable 模型绑定 | Cable 内部 | 唯一客户端模型 ID、客户端支持的别名、显示名称、显式候选来源、选源策略；客户端支持逐模型策略时保存该模型的内置模板选择 |
| 候选来源 | 模型绑定内部 | 供应商 ID、上游模型 ID 及可访问接口引用；启停状态，按已开放策略配置优先级或权重 |

接口、模型和候选来源是所属对象的内部记录，不单独增加管理模块。凭据集中保存，由接口引用，不复制到 Cable。适配实现和提示词模板不是用户可新增的业务对象；Cable 只保存内置策略的选择。客户端别名、启动模型和提示词选择属于 Cable，用户的项目规则仍由客户端管理。

关系为：`客户端类型 → 多条 Cable → 每条 Cable 的多个供应商 → 显式选择的供应商模型记录`。一个供应商模型记录可被多个 Cable 复用。

### 3.1 供应商模型记录

- **上游模型 ID**：请求上游使用的标识，关联的协议接口共用此 ID；与供应商 ID 共同组成记录唯一键，不再生成独立的供应商模型内部 ID。
- **实际模型身份**：实际模型及版本，作为客户端原生支持和适配判断的依据；记录声明来源，无法确认时标记为未知。已知模型类型或能力不等于已确认实际身份。
- **可访问接口**：引用供应商已配置的协议接口，表示该模型可通过哪些接口访问；候选来源只能选择其中的接口。
- **能力与限制**：输入类型、工具调用、推理控制、上下文和输出限制等，必要时按可访问接口记录差异。

不引入各接口独立的上游模型 ID。不同模型 ID 保存为不同供应商模型记录，即使对应同一实际模型；同一供应商内相同模型 ID 维护一条记录及其接口集合。

修改上游模型 ID 等同于移除旧记录、创建新记录，不迁移旧引用。新记录的可访问接口、能力事实及 Cable 选择需要重新配置和校验后生效。Cable 保留原客户端模型 ID 和旧的“供应商 ID＋上游模型 ID”引用，将相关绑定标为“来源不存在”；收到请求时返回明确错误，不自动替换或路由到其他模型。用户可显式重新绑定，之后重新校验适配、能力和历史兼容性。删除模型记录采用相同的失效语义。

### 3.2 模型列表与多来源

默认把勾选的供应商模型记录加入为独立 Cable 模型；客户端 ID 或别名由 Cable 模型绑定管理，在 Cable 内唯一。初始 ID 由客户端适配器生成，保持稳定并符合客户端识别规则。显示名称可含供应商名称，改变显示名称或排序不改变 ID。

同一实际模型在 A、B 两家供应商都有供给时，用户可以选择：

- **分别使用**：两个客户端模型 ID，各自固定来源；可以保留各自能力和窗口。
- **合并来源**：一个客户端模型 ID，显式加入 A、B 两个候选来源；基础阶段手动指定来源，后续开放自动路由、均衡或故障切换。

同名不代表同一模型，不自动合并。首期合并仅面向已支持、身份和历史约定兼容的来源。异构模型合并后续按具体组合实现；必须已有内置兼容规则和配套提示词策略，且共同能力、参数映射及历史策略通过验证，不通过用户编写映射来开放，也不冒用原生模型身份。

同一供应商内不同模型 ID 的记录也可以分别发布，或在兼容检查通过后显式合并来源；不在供应商目录中按实际模型身份合并记录。

手动切换来源同样检查已发布的能力与历史约定。新来源需要改变客户端目录或提示词时先重新应用；历史不兼容时使用新会话，不能直接把原会话移交给新来源。

选择一个供应商只把其模型列为候选，不勾选任何模型。来源必须属于 Cable 已选择的供应商；移除供应商时列出受影响绑定，由用户明确移除或替换来源。绑定无来源时保留为待配置，不自动补入其他模型。

## 4. 供给事实、代码适配与提示词策略

分别判断 **实际模型身份、客户端原生支持、协议兼容、适配实现状态、验证状态**。原生支持是模型与客户端及版本的关系，不是供应商整体属性；同一供应商可同时提供原生和非原生模型。

### 4.1 供应商声明能力事实

能力采用“支持 / 不支持 / 未确认”，附带声明来源。模型供给维护输入类型、工具调用、上下文和输出限制，以及推理控制方式：

| 推理控制方式 | 供给记录的事实 |
| --- | --- |
| 档位 | 上游支持的档位值、默认值，以及是否允许关闭；不假设各模型档位含义相同 |
| 开关 | 是否支持启停、默认状态，以及与其他控制方式的约束 |
| 预算 | 数值单位、最小/最大值、默认值或自动模式，以及与输出预算的关系 |
| 无控制或未确认 | 区分不支持推理、推理不可调及控制方式尚未确认 |

同一模型可以组合多种控制方式；按接口记录差异。用户声明或修正这些事实，不编辑上游字段路径、转换表达式或映射脚本。实际字段名称、结构及转换由代码按支持类型处理。

固定来源使用其能力；自动多来源绑定按候选共同能力和可映射的控制方式发布，限制取最小值。档位、开关、预算不能仅取数值交集或凭模板互换；没有已实现映射时不开放相应选项或拒绝不支持的请求。未确认能力不能作为承诺，来源暂时离线不扩大客户端目录。

### 4.2 客户端适配由代码实现

适配器根据客户端及版本、访问接口协议、实际模型身份或类型和能力选择已实现规则，处理参数、工具及流式事件、错误、模型目录、历史回放与压缩。供应商名称、实例或预设不决定适配规则；同一已支持组合可复用于多个实例。能力声明用于约束已有实现，不会自动生成新协议适配器。

新增类型需要实现、验证和发布代码。未支持的组合可以保存为待配置，但不能通过选择模板或声明能力绕过实现检查；跨协议转换按第 6 节开放。页面不提供自定义映射、工具转换、历史策略或适配脚本编辑器。

### 4.3 Cable 选择客户端提示词策略

| 模型情况 | 默认策略 |
| --- | --- |
| 已确认对应客户端原生模型 | 使用对应版本的原生模型定义和提示词；代码按需生成别名目录，并收紧供应商限制 |
| 已实现支持的非原生模型类型 | 使用 CableTidy 内置兼容模板；有可选内置模板时允许用户选择 |
| 实际模型身份未知 | 保持未知状态；仅在已实现的明确兼容类型满足能力条件时使用内置兼容模板 |
| 已知原生模型不在本机目录 | 更新客户端或由代码补齐对应定义，不以兼容模板掩盖原生定义缺失 |

“默认”由代码根据模型身份和客户端机制决定。模板与工具约定配套维护，选择模板不能改变接口协议、创造模型能力或修改历史规则。用户不新增、编辑或保存自定义模板；项目规则继续由客户端管理。

策略按客户端实际支持的模型、Agent 或会话粒度选择；全局策略保存在 Cable，逐模型策略仅在客户端确有机制时保存在绑定。预览展示生效范围、模板与原生定义版本、配套工具约定。实现可用与真实模型验证通过分别展示。

### 4.4 客户端配置的实施方式（逐项交付）

| 客户端 | 适配落地方式 |
| --- | --- |
| Codex | 原生模型复制对应版本的完整定义；非原生/自定义 ID 生成匹配目录，保留工具约定并显式配置指令、能力和限制。支持时使用 provider 的远程目录，否则生成本地目录并检查全局作用域冲突 |
| Claude Code | 使用真实 Claude 身份映射、模型选择和可生效的能力机制；非 Claude 类型需单独实现与验证内置兼容规则和模板。提示词追加/替换或 Agent 配置受客户端实际作用域限制，不能假设 `/v1/models` 自动选择提示词 |
| Gemini CLI | 保持模型分类、工具定义及 GenAI 参数一致；需要 system 文件时由内置模板生成并按会话配置。只有客户端确有机制时才承诺逐模型提示词切换 |
| OpenCode | 按版本生成供应商模型定义和 Agent 配置；v1 的模型名模板选择与当前 main 的通用提示词方式分开处理 |

以上是各客户端的实现方向，不构成首期全部支持的承诺。第一阶段仅实现第 6.1 节经用户确认的组合；页面仅开放已交付类型。

目录和模型列表只发布该 Cable 显式开放的模型，不能直接转发供应商全部发现结果。客户端自带选项和内部辅助请求按其机制配置；确实无法收敛时在预览中说明并要求明确辅助模型绑定，不隐式扩大路由范围。

全局提示词或目录配置影响多个模型时，生成器检查共同兼容性。无法共存的配置建议拆成多条同类型 Cable，并使用隔离的启动配置；不声称网关改名能触发客户端重建提示词。

## 5. 管理页面逻辑

导航为 **供应商、Cable、审计**。客户端提示词策略在 Cable 内选择和预览，不设预设管理、用户模板保存或通用适配编辑入口。

### 5.1 供应商管理

列表、新建与详情分别为独立页面，沿用 `origin/main` 的线路列表、配置分区、表格、按钮、表单及移动端规范。列表展示名称、状态、接口数和模型数，不嵌入新建或详情表单。供应商管理只维护接口和模型，不展示使用情况、引用 Cable 数或引用绑定列表。

- **新建页面**：基本信息、接口和模型分别使用独立 `panel` 及 `panel-header` / `panel-body`。填写供应商名称，在接口列表通过“添加接口”弹窗录入一个或多个协议、根 URL 及认证；模型列表通过“添加模型”弹窗录入模型供给事实，并关联已添加的接口。允许先不填写模型，创建时至少有一个接口。供应商和接口 ID 由系统生成，用于稳定引用；不要求用户填写，也不按名称重新生成。无供应商类型或预设选择步骤。接口和模型在创建前保存为页面草稿，支持编辑和删除；点击“创建供应商”后一次性校验并保存全部资源，失败不留下部分供应商配置。创建后进入详情。
- **基本信息**：详情以三个并列独立 panel 展示基本信息、接口和模型，沿用诊断/设置页结构，不共用外层 panel 或表单。基本信息单独保存名称及启停状态，接口与模型各自通过弹窗保存资源；名称变化不改变内部 ID、模型记录键或 Cable 引用。
- **接口表**：与模型表并列的独立资源表，展示名称、协议、地址及认证状态，提供添加、编辑、测试连接、发现模型和删除。添加/编辑使用弹出表单。认证选项随协议变化，由内置方式决定凭据字段与必填条件，用户不编辑认证头或前缀。已有凭据留空保留；无需认证时不要求凭据、不发送认证。旧自定义认证可保留原配置，不开放新自定义方式。未交付协议明确标为暂不适配，不能据此宣称真实接口验证通过。
- **模型表**：展示上游模型 ID、实际身份及版本、可访问接口；添加/编辑使用独立弹出表单。手动录入或从指定接口发现，候选经确认供给事实后保存。表单填写实际身份（可未知）、可访问接口、能力和限制，推理按档位、开关、预算记录，接口差异继承公共事实；不提供接口独立模型 ID。保存失败保留输入，取消有修改时确认放弃。不同 ID 保留独立记录，同 ID 发现结果提示重复，不自动覆盖人工确认内容；发现不加入任何 Cable。

修改上游模型 ID 或删除模型记录时，仅提示旧引用不会迁移、相关绑定将变为“来源不存在”，不展示使用情况。失效状态及显式重新绑定在 Cable 管理中处理。供应商及接口删除仍校验引用约束，存在引用时提示先在 Cable 中解除引用，不增加供应商侧的引用管理入口。

### 5.2 Cable 创建

创建采用四步，支持保存草稿：

1. **基本信息**：名称、客户端类型、本地地址。允许同一种客户端创建多条线路。
2. **供应商与模型**：多选供应商；按供应商展示可搜索的模型列表，显示上游模型 ID、实际模型身份和可访问接口，默认不勾选，显示每家“已选数量”。提供显式“选择当前筛选结果”和清空操作。选定模型后，从其可访问接口中选择该来源使用的接口；代码支持状态按具体组合判断。
3. **模型与提示词**：展示已选模型的绑定、供给能力和代码支持状态。默认使用对应原生定义或内置兼容模板，用户只能选择可用内置策略；展示实际生效粒度，无参数映射、工具转换或历史规则编辑。能力事实有误时跳转供应商管理修改。重复模型可分别保留，已支持的兼容来源可显式合并并手动指定来源。
4. **默认与预览**：默认模型只能选 Cable 已开放模型；配置客户端支持的别名、辅助模型和子代理设置。预览完整映射、适配效果、客户端文件变更和问题。

“保存 Cable”与“应用到客户端”分开。缺少来源、代码适配实现、兼容提示词或协议转换时可保存草稿，未通过检查的绑定不发布；默认模型不可用时阻止应用，并明确提示需要修复的项目。

配置完整性、代码支持检查与真实模型验证分开。已实现组合采用内置兼容模板且静态检查通过时可标记为“内置兼容模板，尚未实测”，不能把“模板存在”当作“类型适配已实现”。

### 5.3 Cable 列表与详情

列表展示名称、客户端、供应商数量/摘要、开放模型数、服务状态和客户端配置状态。按客户端筛选但不限制线路数量。

详情包含 **供应商与模型、提示词与路由、客户端配置**：

- 供应商与模型：编辑所选供应商模型记录及访问接口，保留未加入模型的候选列表；模型表分别显示客户端 ID、上游模型 ID、实际模型身份、供应商/接口和问题。旧模型记录移除后仍显示原客户端 ID 和旧上游 ID，标为“来源不存在”，允许用户显式重新绑定。
- 提示词与路由：选择内置策略，查看模板、代码适配版本与实际生效范围；能力事实只读并链接供应商配置。来源组展开成员及手动来源；路由策略按功能开放情况出现，不默认启用自动选择。
- 客户端配置：预览、应用、撤销或导出隔离启动配置。显示目标配置位置、当前激活 Cable、共享字段影响和是否需要重启。

修改客户端类型后重新评估全部绑定，保留用户选择并将不兼容项标为待配置。供应商或来源变化后重新校验；目录/提示词变化标记需重新应用，仅连接信息变化更新运行配置。

多条 Cable 可同时运行。应用 B 到与 A 相同的配置位置时预览激活切换，管理共享字段的所有权和恢复记录；撤销 A 不得覆盖 B 或用户后续修改。运行中的旧客户端仍连接原地址，不因激活切换迁移其会话。

## 6. 请求选源与分阶段开放

```text
请求 → Cable 客户端模型 ID → 供给事实与候选来源
     → 代码支持/能力过滤 → 已开放的选源策略 → 内置适配器 → 供应商
     → 客户端格式响应与审计
```

| 阶段 | 交付能力 |
| --- | --- |
| 1：本次基础重构 | 已确认的 A+B 模型范围；多 Cable、多供应商、显式模型选择；对应类型的内置适配、提示词策略与配置生成；同协议按模型固定选源，兼容多来源手动指定 |
| 2：跨协议转换 | 按协议对交付工具、流式事件、参数、错误和历史转换；通过检查的来源加入可用集合 |
| 3：多供应商自动路由 | 在显式来源中按请求能力、可用性和优先级选源，支持会话/工具回合亲和与决策记录 |
| 4：负载均衡 | 在兼容且可用来源中按权重等策略分配；不打破历史或工具回合约束 |
| 5：故障切换 | 在可重放且尚无客户端可见输出或工具副作用的边界尝试备用来源，记录每次尝试与原因 |

阶段是能力开放顺序，阶段 1 不能退化为单供应商或仅改模型名。各项实现后单独验证、开放，不要求用户重新建 Cable。

### 6.1 首批支持组合（已确认 A+B）

“组合”指 **客户端 × 协议 × 模型类型**；实现时同时约束客户端版本和模型能力。同一种已支持组合可用于多家供应商实例，实例数量不受首期组合数量限制。用户已确认首期选择 A+B：

| 组合 | 客户端 | 协议 | 模型类型与交付重点 |
| --- | --- | --- | --- |
| A：已确认 | Codex | OpenAI Responses | Codex 原生支持的 GPT 模型类型；复用原生定义、档位式推理、工具与历史规则，验证多供应商显式模型选择 |
| B：已确认模型组 | Codex | OpenAI Responses | GLM-5.3、GLM-5.3-Flash、Kimi K3、DeepSeek-V4-Pro、DeepSeek-V4.1-Flash、MiniMax M3；逐模型实现所需内置映射与兼容模板，验证原生与非原生共存 |

B 的六个模型名称按用户指定保存为目标名单，不据名称推断可用性、实际版本或能力。实际供给的上游模型 ID、身份及版本、推理控制方式、工具能力和限制通过接口文档与验证确定；未确认的事实保持未知。不同模型可复用已验证的内置规则，但不能仅因同属 B 就假设能力或历史兼容。

验证供应商及 Responses 接口无需在设计阶段确定，可以在实现准备或集成验证前选择已有配置；不要求一家供应商覆盖全部六个模型。实际调用前需要可用 URL、认证配置、上游模型 ID 及模型身份依据，不在文档中保存密钥。接口未落实不阻碍设计与基于协议文档的实现，但不能标记真实模型验证通过；首期完成验收须覆盖这六个目标模型，缺少验证条件时明确列为未完成，不默默缩减名单。不能把“任意 Responses 兼容模型”当成已支持类型。

**DeepSeek 官方服务已列为验证候选**，用于 B 中的两个 DeepSeek 目标模型，不视为已完成认证配置或真实调用验证：

| 候选服务 | Responses 接口 | 上游模型 ID | 目标模型及待验证事项 |
| --- | --- | --- | --- |
| DeepSeek 官方 | `https://api.deepseek.com/responses` | `deepseek-v4-pro` | DeepSeek-V4-Pro；实际版本、能力和限制需确认 |
| DeepSeek 官方 | `https://api.deepseek.com/responses` | `deepseek-flash` | DeepSeek-V4.1-Flash；官方文档当前说明由 DeepSeek-V4.1-Flash-1017 提供服务，调用时重新确认实际身份 |

官方 Responses 接口采用无状态方式，每次请求需发送完整历史；内置适配须验证历史回放、推理控制、工具调用和流式行为，不能假设支持服务端会话存储或远端历史引用。

**验证分工已确认：**

- GLM-5.3、GLM-5.3-Flash、Kimi K3、MiniMax M3 由用户选择可用供应商并手动验证，无需在设计阶段提交供应商名单。
- 实现方提供逐模型的验证步骤与结果记录格式，覆盖实际身份、推理控制、工具调用、流式输出及多轮历史；用户手动验证结果可作为集成验收依据。未实际执行的项目保持未验证，不要求真实调用全部自动化。
- 需要实际调用时，由用户协助落实 URL、上游模型 ID 和可用认证配置；凭据通过既有配置机制保存，不写入设计文档或验证结果。
- GitHub Actions 继续运行模拟上游的协议、适配和回归测试，真实模型测试不作为 CI 必需项。真实验证在本地或用户环境完成，不新增 GitHub Secrets 或真实调用 workflow。若后续发现必须在 CI 中执行的具体验证需求，再说明原因并单独确认。

当前 CableTidy GitHub Actions 未配置 DeepSeek 官方真实调用；列为候选及上述验证分工不改变 CI 或认证配置。

A 的具体原生模型和 Codex 支持版本按现有环境及完整模型目录确定，形成明确的验证名单；如用户有指定版本或模型要求，以其要求为准。版本选择、内置规则与测试用例属于实现细节，不再逐项要求用户确认。其他客户端、协议及模型类型后续逐项确认与实现。本设计已获实施授权，实施分支从最新 origin/main 创建；真实模型验证按上述分工完成。

### 6.2 运行与切换约束

运行顺序先校验模型与协议能力，再应用历史/亲和约束，最后按可用性和策略选源。自动路由、均衡与故障切换分别配置，任何策略都不能扩大用户选定的候选范围。

同一客户端模型 ID 不同来源之间的能力与历史约定在发布时确定。请求上游时使用选中供应商模型记录的模型 ID，不使用客户端别名替代。签名、加密推理、远端响应引用和原生压缩结果不能假定跨供应商可重放；策略不兼容时固定来源或拒绝切换。已发送的回答不与新来源结果拼接，来源变更不能绕过这些边界。

引用的模型记录不存在时，相关绑定失效并返回“来源不存在”错误；即使有其他候选，也不把记录移除当作临时故障自动切换。由用户显式移除旧来源或重新绑定，完成校验后恢复使用。这与已配置有效来源的暂时不可用及后续故障切换区分处理。

新 Cable 默认拒绝未绑定模型。旧透传线路迁移时保留其行为，并显式指定唯一兜底供应商接口；不把未知模型广播到所有供应商，也不将其列为自动路由候选。

## 7. 审计、生命周期与迁移

审计记录 Cable、客户端类型/版本、客户端模型 ID、内置适配器与提示词策略版本、访问接口、请求发生时的供应商 ID 与上游模型 ID、实际模型身份（含未知状态）、能力修订与验证状态；推理记录客户端请求选项及实际生效控制方式和值。多来源额外记录候选、排除原因、选源原因、亲和和各次尝试。保存请求时修订号及脱敏的生效配置，保留现有检测、响应和错误审计。供应商模型记录删除或上游 ID 修改后，历史审计仍保留请求时的原值，不随当前目录改写；失效绑定的请求记录旧引用及“来源不存在”错误，不记为已调用新模型。

新供应商及接口 ID 由系统生成；既有供应商和接口保留原稳定内部 ID，不要求重新填写或重新编号。Cable 模型绑定由 Cable 内唯一的客户端模型 ID 管理。供应商模型记录仅使用“供应商 ID＋上游模型 ID”唯一键，不设内部稳定记录 ID。删除 Cable 不级联删除供应商、模型记录或凭据；撤销客户端配置继续遵守字段所有权。停用或移除某个来源只影响相关绑定，不能使其他无关模型一并失效。

迁移把现有上游转成供应商接口，当前单上游关系转成 Cable 的单来源绑定；把供给事实与客户端选择分开，缺乏依据的能力保留为未确认。旧模型定义选择转成可对应的内置提示词策略；无法转换的数据保留为迁移记录并标明待处理，不新增通用编辑器。保留线路 ID、地址、凭据、默认模型、模型映射、透传和恢复记录，不按名称或地址自动合并供应商。旧 Route/Virtual Provider 可作临时兼容结构，页面不要求用户维护它们。

迁移按“供应商 ID＋原上游模型 ID”建立供应商模型记录和 Cable 来源引用，不新增模型内部 ID；同一供应商内相同上游 ID 汇集可访问接口及必要的能力差异，不同 ID 保留独立记录，即使实际身份相同。实际模型身份无法确认时标记为未知，不由别名猜测。客户端 ID/别名和原有映射留在 Cable 绑定中；不创建接口独立上游模型 ID、供应商类型或供应商预设依赖。后续上游 ID 修改按删除旧记录、创建新记录处理，不自动迁移 Cable 引用或历史审计。

旧类型在未完成新适配前保留现有运行路径，不宣称已纳入新类型支持；无法保持行为的旧线路暂不迁移。迁移兼容不扩大首期新增类型的验收范围。

**首期验收仅针对用户确认的组合：**

1. 同一客户端创建两条 Cable，独立运行并正确切换/撤销客户端配置。
2. 一条 Cable 选择 A、B 两家供应商的部分模型；供应商新增或同步模型不会扩大 Cable。
3. 供应商列表、新建和详情为独立页面；新建页同时提供名称、接口列表及模型列表，可添加多个接口和模型，编辑/删除草稿后一次性创建；详情基本信息、接口及模型使用三个独立 panel，不共用表单，添加/编辑资源使用弹窗。供应商及接口 ID 自动生成，改名保持引用；认证方式随协议提供，凭据字段随方式变化，无认证头/前缀编辑。界面沿用既有样式并通过移动端检查，不依赖供应商类型或预设；同一已支持组合可用于多个供应商实例。数据允许多协议和不同模型类型共存，首期运行验证只覆盖已确认组合。
4. 同一模型记录在关联接口上使用相同上游模型 ID；不同 ID 保留独立记录。实际身份未知可明确表示，接口能力差异不产生接口独立 ID。Cable 客户端 ID 与上游模型 ID 分别管理，发布和请求映射正确。
5. 对已确认的推理控制方式，供给事实、客户端选项及代码生成的上游参数一致；未实现方式不可凭声明启用。
6. 验收 A 的原生模型定义与提示词，以及 B 六个目标模型的内置兼容规则与模板，并验证二者共存。逐模型记录供给事实和验证结果，不要求一家供应商覆盖全部模型；模板与工具约定一致，选择粒度符合客户端机制，其他组合不计入首期验收。
7. 同一实际模型的来源可以分别发布或按已实现规则合并；手动切换遵守能力和历史约束。停用、移除只影响相关模型。
8. 未交付组合及策略不可启用；页面没有用户适配、参数映射、工具/历史规则或模板编辑器。供应商预设不属于首期数据依赖、流程或验收。
   供应商管理仅展示接口和模型，不包含使用情况、引用数量或引用绑定列表；绑定问题及重新绑定由 Cable 管理处理。
9. 适用旧线路迁移后行为保持一致，模型记录与客户端绑定按上述边界归属；不能迁移的保留原路径，客户端不支持的配置明确报出，不生成无效设置。
10. 供应商模型以“供应商 ID＋上游模型 ID”为唯一键，无独立内部 ID。修改上游 ID 后旧引用保留、绑定显示“来源不存在”，请求返回明确错误且不自动改投其他来源；新记录的接口、能力和 Cable 选择须重新配置并校验。显式重新绑定后方可恢复，历史审计保留原供应商 ID 和上游模型 ID。删除模型记录产生同样的引用失效行为。

**后续按能力分别验收：**跨协议的参数、工具、流式与历史转换；自动路由的显式候选范围与亲和；均衡的权重与约束；故障切换不重复回答或工具副作用。每项均要求审计可还原决策，不提前纳入首期完成条件。
