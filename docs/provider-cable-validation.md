# 供应商与 Cable 首批验证

本分支实现 A+B：Codex 原生 GPT 定义，以及 GLM-5.3、GLM-5.3-Flash、Kimi K3、DeepSeek-V4-Pro、DeepSeek-V4.1-Flash、MiniMax M3 的 Responses 内置兼容规则。代码和模拟测试通过不代表真实供给验证通过。

## 配置与验证步骤

1. 在“供应商”页配置服务名称、Responses 根 URL 和认证。模型记录填写请求上游的模型 ID、实际身份及版本、身份依据、可访问接口、工具/流式/推理能力和上下文限制。未知事实留为未知；供应商发现只返回候选 ID，不替用户判断身份，也不加入 Cable。
2. 推理按接口真实接受的控制方式填写：档位使用 `effort` 及其支持值；预算记录单位和上下限。首期 Responses 适配只开放档位参数；只有预算或开关控制、没有已实现档位映射的接口保存为供给事实，但不可凭声明启用。未确认工具调用、流式或上下文限制的兼容模型不能发布。
3. 创建 Codex Cable，多选供应商，再显式勾选模型并加入绑定。客户端 ID 可以与上游 ID 不同；绑定别名使用同一模型定义和提示词。选默认模型后才能应用。原生 GPT 使用本机完整定义；B 使用兼容或简洁兼容模板。兼容来源声明无状态完整历史。
4. 预览后应用，重启 Codex；或者导出隔离配置，把 `files` 按 `path` 写入独立目录，设置 `CODEX_HOME` 为该目录后启动。应用关闭内置网页搜索，避免辅助模型越过选择范围。兼容定义使用普通 Responses、直接函数工具和 freeform `apply_patch`，关闭原生专属代码模式、内部请求及推理更新项。预览明确说明特殊 tool_search 与 multi_agent_v1 尚未适配，网关不向上游发布这两类工具；其他不支持工具拒绝请求。
5. 在临时 Git 仓库中逐模型检查：普通回答、支持的推理档位、流式结束、读取文件/运行命令、用补丁创建并修改文件、接续工具结果的多轮对话。请求审计应保持客户端 ID、原上游 ID、供应商/接口、身份和推理生效值。
6. 同一 Cable 共存原生 GPT 与 B，分别选择并请求。供应商添加新模型后刷新，Cable 的选择和发布目录必须保持不变。
7. 同模型多来源须声明相同身份/版本、能力、限制和历史约定。显式手动换来源后使用新会话；远端引用、加密推理、原生压缩和推理更新项不可跨来源回放。不存在的任一来源会使绑定失效，不尝试其他候选。删除或修改上游 ID 后检查错误，再显式重新绑定。
8. 应用 Cable A，再应用 Cable B。撤销 A 应拒绝覆盖 B；撤销 B 恢复 A；撤销 A 恢复最初配置。用户修改受管理字段后应保留用户配置并拒绝自动撤销。导入导出需保持选择及来源引用；同名供应商导入为独立实例，无凭据文件不继承本地密钥。

## 本地自动检查

`npm test` 运行供给、绑定、协议与迁移回归。构建测试程序后可运行 `node scripts/supplier-inventory-browser.mjs` 检查显式选择、预览、应用、激活状态和撤销。

已安装 Codex 时运行 `node scripts/codex-inventory-smoke.mjs`，使用独立 `CODEX_HOME` 和本地模拟上游检查原生 GPT 与兼容模型共存、请求映射、工具与流式结果。本机 Codex 0.162.1 已通过；脚本不调用真实供应商，使用独立客户端配置，不作为 GitHub Actions 的必需项。

| 实际身份 | 验证服务/模型 ID | 状态 |

| Codex 原生 GPT | 本机 `codex debug models --bundled` 完整目录；已检查 Codex 0.162.1 | 本地客户端/模拟上游检查，真实上游待验证 |
| GLM-5.3 | 用户配置 Responses 服务及上游 ID | 待用户手动验证 |
| GLM-5.3-Flash | 用户配置 Responses 服务及上游 ID | 待用户手动验证 |
| Kimi K3 | 用户配置 Responses 服务及上游 ID | 待用户手动验证 |
| DeepSeek-V4-Pro | 官方候选 `https://api.deepseek.com`，`deepseek-v4-pro` | 待认证与真实验证 |
| DeepSeek-V4.1-Flash | 官方候选同上，`deepseek-flash`；文档称 V4.1-Flash-1017 | 待确认实际身份与真实验证 |
| MiniMax M3 | 用户配置 Responses 服务及上游 ID | 待用户手动验证 |

DeepSeek 官方 Responses 文档的档位为 `none/low/high/max`；代码将 `minimal` 转为 `low`，`medium/xhigh` 转为 `high`，且只向客户端发布供应商已声明接受的映射。其他四个模型只使用标准 Responses 档位，要求供应商明确提供 function 和 custom `apply_patch`。没有这种接口能力时属于未支持的供给组合，不能因目标模型名相同而宣称可用。预算及开关的专属参数映射待取得对应 Responses 接口依据后逐项实现。

## 结果格式

每个模型保存一条记录，不包含认证凭据：

```text
日期 / 验证者：
CableTidy 分支或提交 / Codex 版本：
供应商名称 / Responses 根 URL / 上游模型 ID：
实际模型身份 / 版本 / 身份依据：
输入类型 / 工具 / 流式 / 上下文及输出上限：
推理控制方式 / 实际接受值 / 客户端选项与上游生效值：
提示词策略：
普通响应 / 流式 / exec_command / apply_patch / 多轮历史：通过或失败
原生与兼容共存 / 显式选择 / 手动来源切换：通过或失败
审计请求 ID / 错误码 / 可复现步骤：
结论：已实测 / 部分通过 / 未验证
```

真实调用在本地或用户环境执行，按已确认分工由用户协助认证。GitHub Actions 继续只跑模拟协议及回归测试，不新增真实模型测试或 Secrets。B 六个模型的真实验证完成前，首批集成验收保持待完成。
