# 凭据保护算法评估与 V2 提案

调研日期：2026-10-16。状态：已实现第一、第二阶段仓库修复，回归验证通过；未部署或修改运行中实例配置。评估代码基于提交 `0c95d6dccc30fd38bc568bfe29dd150cc461b873`，使用本地隔离实例和模拟上游。

已确认的架构要求：统一凭据候选识别、证据和位置；审计与保护复用同一份检测结果。这是本次改造的必要条件，不能仅以共享正则或检测函数替代。

## 1. 建议与边界

建议保留现有可逆占位符、请求隔离、加密暂存和 SSE 还原能力，改造前端的候选提取、凭据判定、映射学习及替换规划。核心原则是：**发现凭据相关文本，不等于发现真实凭据；发现凭据，也不意味着可以修改它出现的所有字段。**

推荐默认方案为“基于证据判定 + 按位置保护 + 有条件的会话复用”。已保存凭据、可信的服务商格式、明确认证值和可确认的凭据字面量可自动保护；代码变量、类型、模板引用、普通标点不能建立映射；证据不足的候选进入低置信审计，不修改载荷，也不自动升级成已知凭据。

“真实凭据”在本方案中表示载荷含有凭据值，而非确认该值当前可用。纯离线算法无法可靠区别同形的测试 Key、过期 Key 和有效 Key；不应通过在线试用凭据来决定是否保护。短密码、低熵密码仍可能是真实凭据，不能仅以长度或熵作为全局放行条件。

## 2. 当前链路的问题

| 环节 | 当前行为 | 实际后果 |
| --- | --- | --- |
| 格式检测 | `TOKEN` 混合 API Key、GitHub、AWS、JWT 等宽泛表达式 | 格式变化缺少版本管理；临时 AWS `ASIA` 未覆盖；JWT 仅看外形 |
| 赋值检测 | 凭据关键词后用正则截取引号或裸值 | 把 `api_key:plain`、`token:string`、`secret: &str)`、成员访问和函数调用当成值 |
| 结构检测 | 凭据字段及继承的 `forced` 语义覆盖整段字符串 | 缺少“实际数据”“代码定义”“普通容器”的区别；非字符串值直接拒绝 |
| 模板与示例 | 全局排除部分词语和模板外形 | `[REDACTED]` 仍误替换；真实密码 `test`、`changeme` 可能被静默放过 |
| Cookie / URL | Cookie 常按整串学习；URL `sig` 等泛化名称参与识别 | 普通偏好 Cookie 被保护；多个值、分隔符和非认证签名混为一项 |
| 映射学习 | 扫描命中立即进入同一无来源的已知值集合，随后再扫一次 | 弱证据被提升为强证据；一次误识别影响整个请求和后续请求 |
| 替换 | 对已学习 A 使用无边界子串匹配，遍历广泛 JSON 字符串 | `plain` 进入 `plain_source`；工具 grammar、描述、协议标识都可能被修改 |
| 出站校验 | 复用同一映射匹配，要求 A 消失 | 能发现漏替换，但无法发现误替换和结构损坏；简单“跳过 grammar”还会触发校验失败 |
| 风险审计 | 与保护共享部分识别原语，但已知值匹配策略不同；字段命中可被当成高置信 | 降低保护误报后，审计仍可能产生高置信误报；两套结果难解释 |

直接依据：`src/security/capture.rs` 的 `ASSIGNMENT`、`protection_ranges`、`placeholder_value`、`learn_fields`；`src/protection.rs` 的 `Scan::end`、`Registry::prepare_at`、`literal_candidates`、`transform_except`、`check_outbound`；`src/security/rules.rs` 的 `annotations_uncached`。

### 2.1 已确认的协议破坏

历史审计显示，07:24 的首个失败请求刚学习 `plain` 就收到 404，映射并未过期。它在工具 Lark grammar 的两处 `plain_source` 内发生替换。08:37 的另一个新上下文重复了相同问题。

上一轮使用实际失败上下文完成的对照：

| 请求 | 上游结果 |
| --- | --- |
| 原文，移除已保存的真实认证信息 | 200 |
| 隔离 CableTidy 实例捕获的实际保护正文 | 404 |
| 同一保护正文，仅恢复 custom tool 的 `format` | 200 |

官方 OpenAI 文档说明 Lark terminal 与 rule 有不同命名约定 [S6]。替换后的 `CTSEC_v1_…_source` 破坏了原 grammar；上游以模糊的资源不存在错误返回。失败请求未携带顶层 `previous_response_id` 或 `conversation`，与历史响应 ID 的失效无关。

### 2.2 本机审计样本

读取最近 8,000 条审计行，取其中 265 条已开启凭据保护的请求，包含此前人工排查和重复重放。共 27 个不同映射原值、1,072 条映射证据和 7,462 次请求替换。

| 人工确认的非凭据内容 | 请求替换次数 |
| --- | ---: |
| 单个反引号 | 4,270 |
| `plain` 变量 | 1,485 |
| `special` 变量 | 469 |
| `body.metadata.api_key` 成员表达式 | 201 |
| `&str)` 类型片段 | 72 |
| `{relay:upstreamSecret` 对象表达式片段 | 67 |
| 其余确认的代码片段、模板截断和标点 | 28 |
| 合计 | 6,592 |

这 6,592 次占样本操作数约 88.3%，但**不是生产误报率**：相同请求被反复重放、没有随机抽样、其余值也未完成标注。样本说明的是误识别会被映射学习和无边界替换大幅放大。单个反引号的来源包括 Markdown 中的 `` `api_key:` ``，并非认证信息。

脱敏统计保存在 [audit-sample-summary.json](research/credential-protection-v2/audit-sample-summary.json)，不包含真实 Key、会话 ID 或完整请求。

### 2.3 可复现的隔离基线

构造 48 个用例：23 个非凭据、20 个含合成凭据、3 个语义不确定用例、2 个结构与会话污染检查。普通用例使用独立会话，不调用真实模型，也不验证合成 Key 的有效性。

| 项目 | 当前结果 | 含义 |
| --- | --- | --- |
| 23 个非凭据用例 | 15 个正文被改变，65.2% | 明确存在变量、类型、标点和配置路径误替换 |
| 20 个含合成凭据用例 | 18 个正文被改变，90% | 仅为“发生替换”的用例命中率；未证明每个凭据字节正确保护 |
| 漏检 | `DATABASE_PASSWORD=…`、裸 AWS 临时访问 ID `ASIA…` | 后缀凭据名称与服务商格式存在缺口 |
| 认证头与 Cookie 范围 | Bearer/Basic scheme 被改写，普通 `theme=dark` 被吞入替换 | “发生保护”并不保证保护范围正确；分隔与非凭据语义也需验收 |
| grammar 完整性 | 失败 | `plain_source` 被改写 |
| 后续请求隔离 | 失败 | 无新凭据的后续请求仍改写 `plain_source` 和普通说明 |

该集合刻意包含难例，用于定位缺陷，不代表常见业务流量。当前结果不得转写为通用检出率或精确率。真实评估还需核对正确范围、未保护字节、非凭据字节变化及上游接受结果。

运行方式：

```sh
node scripts/build-native.mjs --debug --test
node docs/research/credential-protection-v2/evaluate-current.mjs
```

结果默认写入被 Git 忽略的 `.cabletidy-debug/credential-protection-evaluation/`。已保存 [current-baseline.json](research/credential-protection-v2/current-baseline.json)；评估脚本不对现有算法添加“必须通过”的断言。

## 3. 外部方案调研

| 来源 | 有效做法 | 对 CableTidy 的适用性与限制 |
| --- | --- | --- |
| Gitleaks [S1] | 服务商规则、secret 捕获组、按规则熵门槛、关键词预筛、局部过滤条件 | 借鉴规则管理与明确捕获值；不直接照搬大正则或全局文件忽略 |
| detect-secrets [S2] | Regex、Entropy、Keyword 分工；变量间接引用、UUID、模板等过滤 | 借鉴代码表达式识别、标注与调参；不能全局排除 UUID 或所有 `$` 开头值 |
| TruffleHog [S3] | 分离 detected、verified、unknown；规则化检测、解码和可选验证 | 借鉴证据来源与验证状态；其联网验证不适合默认请求转发路径 |
| GitHub Secret Scanning [S4、S5] | 服务商、通用、AI 密码规则分类；识别与阻断覆盖不同；通用认证头精度为 Medium | 自动修改比告警代价更高，必须采用明确保护条件；密码不能只靠 token 外形 |

Gitleaks 当前通用 API Key 规则使用最小长度与熵约束，AWS 规则包含 `ASIA`，服务商规则有专门格式。detect-secrets 明确说明单靠格式会影响 recall，Keyword 可以捕获不随机的密码，但需要过滤；其 `is_indirect_reference` 对函数调用和下标访问做专门识别。GitHub 对通用模式不提供 validity checks，对 AI 检出的密码不提供 push protection [S4]。这些资料共同支持“不同证据使用不同动作”，不能据此推断某一工具可以完整解决代理改写。

建议第一版使用本地、确定性检测。完整引入扫描 CLI 会增加运行时依赖、启动与内存成本，而且这些工具主要处理文件或仓库，不保证 JSON、工具 schema、grammar 与 SSE 的可逆语义。若复用规则实现，应锁定版本并核对许可证；源码引用不等于允许直接复制。

不建议把待判断文本发送给云端模型，也不默认试用发现的凭据。联网验证增加请求时延和外部操作，失效/验证失败也不代表应放行；需要这类能力时应作为独立、明确启用的离线审计任务。

## 4. V2 算法提案

### 4.0 一份检测结果，两个消费者

统一检测器对原文载荷产生不可变的 `CredentialDetection`。审计生成风险记录，保护生成替换或拒绝决策；两者均引用该结果中的同一候选 ID、证据与原文位置。审计不得重新跑一套凭据正则，保护不得重新发现候选或通过会话映射另建无边界匹配路径。

| 层 | 输入 | 输出与职责 |
| --- | --- | --- |
| 统一检测 | 原文快照、协议角色、冻结的已登记/可信会话凭据目录、检测规则版本 | `CredentialDetection`：候选、证据、位置、覆盖状态及检测上下文版本 |
| 审计决策 | 同一 `CredentialDetection` 与审计策略 | 候选对应的风险类别、置信档位和展示；不改变载荷 |
| 保护决策 | 同一 `CredentialDetection` 与保护策略 | 候选对应的替换范围、不可安全修改原因、所需 A↔B 映射 |
| 执行与记录 | 保护计划、原文及执行结果 | 执行替换/还原，校验结构与计划；按候选 ID 回写实际操作证据 |

`CredentialDetection` 至少记录 `snapshotId`、检测规则版本、可信目录版本、候选列表、完整/部分/不可检查的覆盖状态。候选位置属于明确的原文快照，包含有序路径、原始字节范围、解码字节范围与编码层级；重复 JSON 键的出现分别定位，不能仅凭字段名合并。审计展示、替换和出站校验均使用这些位置，不从修改后的正文重新推导原文位置。

检测判断、处理策略与实际执行结果分别记录。`AuditDecision` 与 `ProtectionDecision` 分开记录策略版本并引用候选 ID；审计与保护使用相同的候选类别、来源、证据和位置，分别决定告警与保护动作。置信度是检测判断，不能直接决定“已替换”或“未替换”状态。

| 记录项 | 含义 |
| --- | --- |
| 检测判断 | 是否为疑似凭据、凭据类别、依据及置信档位 |
| 保护决策 | 根据保护开关、策略和位置语义，决定尝试替换、不替换或阻止转发 |
| 实际替换结果 | 该候选具体位置实际完成替换且通过校验才记录“已替换”；未完成则记录“未替换” |
| 未替换原因 | 如保护关闭、策略未选择替换、结构中无法安全替换或执行失败；原因不是第三种替换状态 |
| 请求转发结果 | 请求是否实际发给上游；独立于某个位置是否完成替换，另记未转发原因 |

“低置信候选默认只作审计提示、不自动替换”是本提案的策略建议，不是统一检测结果的必然要求。高置信凭据在开启保护且可以安全修改时尝试替换，但仍需依据执行结果记录状态。例如：成功替换后才记录“已替换”；保护关闭时记录“未替换，原因：保护关闭”；结构中无法安全替换时记录“未替换，原因：结构中无法安全替换”，并阻止请求转发；执行失败也不能记录“已替换”。多处出现分别记录结果，请求汇总依据实际操作次数生成，不能用置信度推导替换状态。

功能开关保持独立：

- 审计开启、保护关闭：统一检测仍运行，审计消费结果，正文原样转发。
- 审计关闭、保护开启：统一检测仍运行，保护消费结果；没有审计持久化不影响保护。
- 两者开启：检测结果生成后立即用于保护，并交给异步审计；异步保存不得触发第二套检测，也不阻塞转发等待数据库落盘。
- 两者关闭：不为这两项功能额外执行凭据检测；其他安全审计规则按各自设置运行。

“复用结果”按载荷快照定义。请求原文和响应原文是不同输入，需要分别检测；SSE 可按通道增量形成结果。B→A 还原依赖当前请求映射，响应审计使用客户端实际看到的还原后原文及操作证据，不把 B 当作新凭据重新学习。保护后的校验可以检查计划执行与结构不变，但不能另设一套候选识别规则。检测器内部允许有界多遍扫描以处理后出现的凭据声明，完成后只发布一份冻结结果供两者消费。

### 4.1 先记录候选与证据，再作保护决定

候选至少包含：候选 ID、准确的原始与解码字节范围、来源路径、载荷角色、提取规则与版本、值类型、正面/反面证据、凭据类别及置信档位。审计和保护决策引用候选 ID；实际替换结果、未替换原因及请求转发结果另记为执行证据，不混入检测事实或预先写入决策结果。

`valueType` 区分 `literal`、`reference`、`expression`、`type`、`template`、`masked`、`unknown`。`payloadRole` 区分内容、实际参数值、工具定义、协议标识和签名/加密块。第一次候选扫描不能动态把所有命中塞入 `Redactor.secrets`；同一次扫描的提取结果应不依赖字段出现顺序。

使用可解释的证据档位，初期不输出未经校准的概率分数。下表为保护开启时的默认策略建议，描述拟采取的动作，不代表实际替换状态：

| 证据 | 默认策略建议 | 会话学习 |
| --- | --- | --- |
| 与本地已保存/明确登记凭据一致 | 可修改内容内保护；不可修改结构内确有凭据值则拒绝 | 精确登记来源优先于模板/示例排除 |
| 可信服务商格式、结构有效的私钥 | 可修改内容内保护；结构内按后述规则处理 | 允许强映射复用；保留“格式命中，未验证活性” |
| 实际 JSON 认证字段、解析出的 Authorization 值、URL 认证值、凭据赋值字面量 | 保护实际值，包括短密码；不吞掉 scheme、键和分隔符 | 按类别使用范围受限的映射 |
| 通用高熵值、无认证上下文的 JWT 外形、不完整解析的疑似凭据 | 低置信审计，默认不改写 | 不进入全会话已知集合 |
| 明确代码引用、类型、模板、遮罩标记、普通标点 | 不作凭据命中 | 不学习；保留调试级排除理由即可 |

同一个值可由多种证据支持。重复出现次数与“已经被弱规则学习过”都不能作为自动升级理由。弱候选必须获得独立强证据，才能提升。

### 4.2 识别上下文中的真实值

1. **实际结构数据**：对 JSON、受限嵌套 JSON、URL、Authorization、Cookie 使用对应解析器，保留重复 JSON 成员与 UTF-8 偏移。不能用序列化成 `Value` 后丢掉重复键的方式替代当前流式保证。对字段词元采用分段识别，如 `DATABASE_PASSWORD`、`DB_PASSWORD`、`STRIPE_API_KEY`，同时排除 `password_policy`、`token_count`、`secretRef` 等非值语义。
2. **源码**：识别确定的字符串字面量、变量引用、成员访问、函数调用、类型声明、比较与正则。`api_key:plain` 中的 `plain` 是引用；`password="hunter2"` 中的 `hunter2` 是字面量，仍应保护。纯字面量拼接可有界解析，动态插值和未知语言不能凭正则截断结果建立强映射。第一阶段使用有界 lexer 和少量明确语法，复杂语言解析器按评估收益后续引入。
3. **`.env` 与 shell**：`PASSWORD=hunter2` 是实际值；`PASSWORD=$PASSWORD` 是引用；`${VAR}` 和含插值的 template 保留引用语义。工具名称或文件名只是辅助线索，不是可信声明；“文件在 test/ 下”不能使真实格式 Key 自动放行。
4. **Markdown、文档与模板**：解析引号、反引号、转义与模板闭合，避免把 `` `api_key:` `` 后的反引号截成值。`[REDACTED]`、`YOUR_API_KEY_HERE` 是显式遮罩/插槽；普通词 `test`、`changeme` 仅在明确示例上下文中降低置信，不能在实际认证字段内全局免检。
5. **服务商格式**：按版本管理前缀、长度、字符集、可离线验证的校验段及上下文条件。覆盖 AWS `AKIA` 与 `ASIA` 等明确格式；访问 ID 单独注明“认证标识”，不声称仅凭它即可登录。旧格式和兼容网关 Key 可通过通用认证上下文或本地登记兜底，不以单一品牌最新格式作为唯一检出条件。
6. **JWT 与私钥**：JWT 有界 base64url 解码、验证 JSON 结构，但不校验签名、不据 `exp` 过期放行；认证上下文中的 JWT 保护，其他位置区分候选与个人信息策略。私钥按封装与结构识别，截断的强特征作为未完整检查处理，不能伪装为已安全保护。
7. **Cookie / URL**：逐个识别 cookie 值，默认保留 `theme=dark; locale=en-US` 等普通偏好；明确会话/认证 cookie 与凭据形值按范围保护。自定义 cookie 名和 URL `sig`/`signature` 缺少上下文时是候选，不按名称一概保护。真实密码即使包含 `$`、引号、中文或很短，也要在可信认证语义下处理。

熵仅用于泛化规则的辅助判定。UUID、SHA、长英文说明、代码标识符的熵可能很高；密码可能很低。不得用一个统一阈值处理全部类别。

### 4.3 映射携带学习来源和匹配边界

映射除现有 A、B、创建/闲置时间外，增加 `evidenceClass`、`credentialType`、`ruleVersion`、`matchPolicy`、`allowedRoles`。候选提取完成后，冻结强值目录，再对允许的位置执行规划；不要让正文扫描次序决定后续命中。

建议匹配策略：

- 服务商 Key、私钥、明确登记的值：在普通内容或解析出的实际值内按凭据单位匹配；可覆盖嵌入正文的真实值。可判断的协议标识、grammar 标识符不使用普通内容的匹配规则。
- 自发现的短值、低熵密码：只在完整实际参数值、认证值或明确字面量位置替换。后续普通句子中出现 `plain` 不能自动视为密码；不替换 `plain_source` 的子串。
- 显式强值确实内嵌于文本或编码内容：在支持的编码层级内保护；对短值不确定的嵌入位置标记覆盖不足。语义歧义不能被“所有子串都替换”消除。
- 响应还原：仅还原本次请求持有的当前会话映射的完整 B，维持随机占位符和跨会话隔离；与 A 的置信判定分开。

已有会话的坏映射需要处理。规则版本升级后，旧弱映射不得继续作为检测/替换依据；可以暂留为同会话、还原专用记录直到原闲置期限，避免仍在上游历史中的 B 无法恢复。活跃请求保有原映射快照。新请求必须重新判定 A；不能从审计数据库自动重建可信目录，也不能凭反复复用提升旧弱映射。

### 4.4 协议结构与内容使用不同规则

不要只在原有全局字符串替换上增加黑名单。规划时要携带真实协议路径和角色，并统一传给扫描、替换、出站验证与审计。

| 位置 | 处理要求 |
| --- | --- |
| 用户/开发者文本、工具结果中的普通内容 | 检查并按规划范围替换；真实 Key 不能因位于文档/源码而免检 |
| 工具实际参数 | 解析支持的 JSON 与字符串层级；替换真实值，保持参数名和编码有效 |
| `type`、`name`、`id`、`call_id`、`tool_use_id`、模型 ID、历史引用、事件路由字段 | 使用结构语义判断；保持标识与引用关系；确有强凭据值且无法安全转换时拒绝 |
| custom tool grammar、正则、工具格式定义 | `plain_source` 等规则名保持原文；真实凭据字面量或强凭据值确实出现时，不发送原值，也不任意改写，返回明确的结构内凭据错误 |
| JSON Schema 元数据 | 保护结构、类型和属性名称；实际 credential `default`/`example` 可按值语义处理；`const`、`enum`、pattern 涉及约束，不得无验证地改写 |
| 签名、推理加密块、二进制/未知编码 | 保留不可修改语义；明确区分不可检查与检测到强凭据；维持现有有界/失败策略 |
| 未知扩展字段 | 仍检测真实凭据；只有普通数据且可安全修改时替换。无法确认语义时记录覆盖不足；强凭据且无法安全转换则拒绝 |

工具定义不是可信免检区。若真实 Key 写在 grammar 的字符串常量里，应报出“工具定义包含无法安全替换的凭据”，而不是原样泄漏。`plain_source` 则是非值结构，不因其部分字节与已知短密码相同就判为泄漏。实际字段恰好等于已登记真实凭据时，不能被结构名称白名单静默放过。

Schema 的 `default`/`example` 与 `const`/`enum` 需要区分：后两者决定允许值。是否提供成套约束映射需要专门验证；第一版遇到不可保持语义的强凭据约束直接拒绝，说明具体路径，避免静默扩大或缩小工具接受范围。

### 4.5 统一规划、校验与错误说明

替换器消费确定的范围，不重新猜测凭据。出站校验同时验证：强凭据在可修改内容中没有残留、计划范围都已保护、未授权字节未改变、标识与 grammar/schema 保持所需语义。

“JSON 仍能解析”不足以证明成功。应对已知结构字段做等值/引用关系校验；grammar 修改被禁止时直接确认字节等值，不为每次请求启动 grammar 编译器。需要验证复杂工具 schema 时，可在独立回归中使用实际校验器。

URL/附加请求头和选定模型使用同一候选证据、角色策略，避免正文已不把 `plain` 当凭据，参数检查却继续用无边界 `contains` 拒绝。连接上游的认证头仍从配置注入，不参与上下文替换。

错误应区分无法保护的真实值、不可检查内容、预算不足和响应还原失败；包括位置与规则原因，但不在普通日志中输出 A。低置信候选不触发“检测到真实凭据”的错误。

风险审计与保护消费同一份候选检测结果，动作分别决策；不能各自重新提取证据或位置。字段名提示不能自动标为 `known_credential_match`；“识别到候选”“实际已替换”“实际未替换及原因”分开统计，请求是否转发独立记录。排除项只作可选调试资料，避免把大量代码标识符换一种形式继续塞满风险列表。

## 5. 方案选择

| 方案 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- |
| 仅精确登记 + 服务商格式 | 最容易控制误报与稳定性 | 漏掉通用 token、数据库密码和无前缀凭据 | 可作为短期保守模式，不作为最终默认 |
| 证据判定 + 语义位置 + 受限映射 | 保留低熵与通用凭据能力，解释误报并限制破坏范围 | 需要重构候选模型和协议角色 | 推荐默认路线 |
| 更宽的熵/关键词/模型检测 | 可找到更多不规则候选 | 候选多、解释和延迟成本高；不适合直接改写 | 仅作可选审计补充 |

第一版不提供全局“激进保护所有候选”开关，也不提供正文里的 `allowlist` 指令作为绕过入口。若需要例外，只接受本地用户配置的规则 ID + 路径 + 精确范围约束，记录版本与影响，不从上游文档或工具结果自动采纳排除规则。

## 6. 评估与验收

### 6.1 建立带来源的语料

在当前 48 用例基础上，至少建立 600 个独立标注片段，另加 100 个多轮/结构回归。按源码、`.env`、实际 JSON、Markdown、URL/认证头/Cookie、服务商格式、schema/grammar 分层；每层包含正例、负例和语义不确定例。

正例使用本地生成或公开规范允许的合成值，不试用真实 Key；已登记低熵密码、自定义名称、新旧格式、Unicode、引号和重复 JSON 键单独覆盖。保留真实失败上下文的脱敏最小复现，不把完整私有审计正文提交到仓库。

按内容来源与基础值划分调参集和留出集，防止同一个值改写几种形式后跨集合泄漏。重复会话按源样本归一，不将一次误判的数千次替换当成数千个独立负例。含强凭据的源码/测试/文档必须进入正例，不能以目录排除替代标注。

### 6.2 指标与初始发布门槛

以下是拟定验收目标，不是已经获得的性能承诺：

| 指标 | 计算与目标 |
| --- | --- |
| 保护精确率 | 正确保护的凭据实例 / 全部自动保护实例；留出集 ≥99%，同时报告样本数和区间 |
| 负例改动率 | 非凭据实例/请求被改变的比例；必须单列源码、文档、协议结构，不用总均值掩盖薄弱层 |
| 强证据凭据覆盖 | 测试集中的登记值、支持的服务商格式和明确认证字面量 100% 正确保护或明确拒绝；拒绝与成功替换分开报告 |
| 通用凭据召回 | 分层统计已支持类别，初始目标 ≥95%；不含无上下文无法判断的任意字符串 |
| 泄漏字节 | 强凭据应保护范围的原文残留为 0；正例“仅改了别处”不能算成功 |
| 结构完整性 | grammar、schema 元数据、标识/引用关系、事件路由不得有未经规划的改变；当前两项污染检查必须通过 |
| 检测结果复用 | 审计和保护引用同一快照、候选 ID、证据及位置；两者开启时不执行两套候选检测；单独开启任一功能仍正确工作 |
| 可逆与流式 | 已支持 JSON/SSE/嵌套编码、初始事件、跨片段 B、工具参数还原全部通过；未知与其他会话 B 不还原 |
| 有界性能 | 相同硬件、并发与正文大小比较 p50/p95/p99、峰值内存、暂存和错误率；初始要求 p95 保护开销不超过基线 1.2 倍，内存预算不增加 |

零失败只表示当前有限测试通过，不代表全部生产输入无误报。低熵密码、编码内容、动态模板、不可见上游历史各自说明覆盖边界。

保留全局资源限制、支持的解码层级、重复键与无效 JSON 行为。性能优化优先关键词预筛、规则分组和本请求候选复用；确认映射数/正文大小造成的开销后，再评估多模式匹配，避免先引入大型解析与模型依赖。

### 6.3 影子评估与迁移

新检测器先在脱敏离线回放和模拟上游运行，比较 V1/V2 的候选、实际改动与结构校验。真实业务灰度应在获得授权后执行，不能把“影子模式”解释为默认允许真实凭据裸发，也不能自动用两份正文向真实上游重复请求。

同一请求只采用一个出站决策；影子结果仅计算差异。对于当前误改会使请求失败的线路，应保持用户明确选择的临时配置，待达标后逐线路开启 V2。旧弱映射降级为还原专用，审计历史维持原规则版本，不重写原始结论。

## 7. 分阶段实施

1. **统一结果与结构止损**：建立检测结果契约，先接通审计和保护两个消费者；统一协议角色与替换边界，修正“所有字符串都可改”；让 grammar/标识、短值子串、跨请求污染回归通过。强凭据在不可修改结构里仍明确拒绝。需要同步改变出站校验，不能只添加 skip。
2. **候选提取与学习改造**：引入来源/类型/证据；解析实际认证值；排除源码引用、类型、比较与标点；取消弱命中即时全会话学习。完善 `[REDACTED]`、Cookie、后缀字段和 AWS 临时格式。
3. **审计呈现与性能校准**：完善保护/告警决策呈现，更新高置信标记，建立规则版本迁移；完成留出集、流式、复用契约与并发校验，再进行授权灰度。

建议按上述三批独立变更评审。第一批建立结果复用并解决协议损坏，第二批降低误报并补齐明确漏检，第三批完善审计呈现与验收。结果复用从第一批落地，不能拖到最后才尝试合并两套算法。现有 TTL、映射隔离与流式资源模型无需作为本次误报治理的首要改动。
