# 请求历史折叠与风险检测复用方案

状态：方案已确认，首版已实现。原始方案材料提交：`9edd782`。调研日期：2026-10-11。

已补充 [Codex 与 Claude Code 的会话上下文管理调研](agent-context-management-research.md)。官方资料及本机模拟请求表明，同一个会话头可以涵盖主线程、side 或 fork 的不同上下文；本方案已据此区分会话归组、上下文身份和检测缓存。

## 1. 当前实现与结论

当前架构可以支持这项改动，但需要共同建立条目指纹和检测结果索引，不能只修改页面的展开状态。

| 现有能力 | 调研位置 | 对方案的影响 |
| --- | --- | --- |
| 请求按协议投影为有序条目，包含角色、类型、工具关联和原文字节范围 | `src/security/content.rs` 中的 `Projection`、`build_index`、`page` | 在现有条目上增加历史关系，保留原编号和原文定位 |
| 每页最多 40 项，详情默认读取第 0 页，所有普通条目默认展开 | `src/security/content.rs`、`web/app.js` 中的 `renderRetainedContent` | 只增加折叠仍可能需要翻过大量历史页，必须增加面向新增内容的读取方式 |
| 内容索引缓存按请求与 manifest 校验，只缓存位置等元数据 | `src/security/content.rs` 中的 `Cache` | 当前没有跨请求内容匹配，也没有风险检测缓存 |
| 会话标识按 provider 与协议隔离，无标识时每条请求独立；只保存一个归组键 | `src/security/session.rs` | 保留会话归组，增加 thread / agent 身份和明确的继承关系；不把归组键当作唯一上下文 |
| 请求结束或中断后进入后台检测，最多并发 4 个任务 | `src/security/mod.rs`、`src/security/pipeline.rs` | 检测复用放在后台，不使代理转发等待先前请求检查完成 |
| 内容、工具参数和敏感位置均重新扫描；finding 去重状态仅属于当前 Pipeline | `src/security/pipeline.rs`、`src/security/rules.rs` | 需要显式缓存已完成的检测结论，包括没有命中的结果 |
| 凭据匹配依赖本地密钥、请求与响应头、结构化及内嵌凭据学习 | `src/security/capture.rs`、`src/security/pipeline.rs` | 内容相同而有效凭据集合变化时，原检测结果可能不再成立 |
| 风险证据绑定当前请求、快照及字节范围；会话发现数累加各请求发现数 | `src/security/store.rs`、`web/app.js` 中的 `contentFindings` | 复用时必须重建当前记录的证据关联，统计必须区分历史携带与新增出现 |

推荐首版先补齐上下文身份，再共同解决阅读和重复规则检查，继续为每条请求独立保存完整正文。正文存储去重会改变留存、清理和原文寻址，单独作为后续优化评估。

## 2. 默认阅读体验

“请求内容”页签默认采用历史折叠视图，新增条目展开；连续的历史条目在原位置合并为一个折叠区间。顶部展示完整内容数量、新增数量、历史数量，并提供紧凑排列的“跳到新增”和“展开全部 / 折叠历史”切换按钮。

例如，第 12 条请求共 86 项，其中 80 项已在前面的请求出现：

```text
请求内容：86 项 · 新增 6 项 · 历史 80 项

▶ 第 1–80 项：已有历史 · 包含 2 项风险 · 展开
  第 81 项：历史模型消息                         [展开]
  第 82 项：工具调用                             [展开]
  第 83 项：工具结果                             [展开]
  第 84 项：用户输入                             [展开]
  第 85 项：用户输入                             [展开]
  第 86 项：其他内容                             [展开]
```

这里“历史模型消息”是协议中的内容类型；如果它首次进入请求正文，仍属于本次新增条目。

交互要求：

- 首次打开直接读取折叠区间摘要和新增条目，不先下载历史正文；历史占用前几千项时，也不需要翻到第几十页才能看到新增内容。
- 历史区间展开后，从当前请求自己的正文分页读取，保留第 1–80 项等原编号。较长区间继续分组加载，“展开全部”也通过分页按需加载，不拼装整份正文到浏览器内存。
- 历史与新增交错时，分别在原位置折叠多个历史区间，保持 `历史 → 新增 → 历史 → 新增` 的先后关系。
- 没有新增内容时明确显示“本次请求内容与已记录历史一致”，完整正文仍可展开查看。
- 区间标题保留类型概况、风险数量和最高严重程度。点击风险自动展开目标区间、加载所在页并定位高亮；每项仍可查看当前请求中的原文。
- 手动展开状态在当前记录的翻页、风险高亮刷新中保留。切换到另一条记录采用其默认状态。
- 第一条请求、缺少可靠会话标识或无法可靠比较时，按完整内容展示。原始内容页签继续查看该记录自身的全部留存正文。

工具定义沿用现有单独折叠的入口，增加“新增 / 发生变化 / 与历史相同”的状态，不与对话重新排序。

## 3. 如何判定重复历史

### 3.1 比较范围与粒度

会话归组沿用同一配置入口和协议的边界，另保存上下文身份、父上下文、fork 来源及请求类别。Codex 使用可靠的 thread ID 区分上下文，Claude 使用可靠的 agent ID 或类别信号；只有会话头时不假定所有请求来自一条线性主历史。

历史比较优先限定同一已识别上下文。明确 fork / 继承关系时，允许比较已验证的父上下文来源；身份不足时只在同归组内保守比较明确相同的历史区间，不据此补造主 / side / 子 agent 关系。请求先后沿用持久化审计序号，不使用后台检测完成顺序。

- Codex：按 `instructions`、`input` 条目、历史引用及工具定义建立指纹。
- Claude Code：按 `system` 与消息内容块建立指纹；消息角色属于比较上下文，`user` 消息内的工具结果继续按工具结果处理。
- 指纹包含完整结构与内容，以及角色、类型、工具名称和调用 ID 等上下文。消息序号、正文偏移和分页位置不属于内容本身。
- 使用带版本的流式 SHA-256 指纹，忽略 JSON 字符串之外的格式空白，保留字符串中的全部空白、数组顺序和对象键顺序。键顺序变化可以保守地算作变化，不需要为排序组装整棵 JSON。
- 参数中的字符串保持字符串语义，不把所有看起来像 JSON 的字符串再次规范化；签名、加密数据、缓存元数据和未知字段都参与完整性比较。

展示匹配和检测匹配采用同一份条目索引，但各自有独立的有效性条件。可以确认内容是历史，并不表示已经完成风险检查。

### 3.2 匹配算法

采用“共同前缀优先、明确锚点补充”的保守方案：

1. 优先与同一上下文最近一条可比较请求进行有序的一对一前缀匹配，覆盖通常的历史不断追加情况。主线程与 side / 子 agent 的请求交错时，不将全会话最近一条当作唯一前驱。
2. 明确 fork / 继承关系时，其首次请求中的完整相同继承部分可以折叠，标明来源；新增任务与分叉后变化内容展开。历史被裁剪、插入或局部改写后，使用完整条目指纹、可靠调用 ID 或明确的连续序列作为锚点，匹配后续的未变化区间；必要时查询允许范围内已留存的更早索引。
3. 不做无界的两两请求比较或整份正文 LCS。候选查询和匹配工作有预算，超预算或无法确定连续关系的部分按新增展示。
4. 相同文字出现多次时按出现位置与序列关系区分；无法消除歧义时不折叠。当前请求追加的一条“继续”，不会因为历史中有另一条“继续”而消失。字符串 `input` 或不携带历史的单消息请求，不能仅凭前一次有相同文字判作历史；完整重复但无法分清重试与再次输入时，提示内容相同并保守展开，不合并事件。
5. 同名工具执行相同参数、但调用 ID 不同，是新的调用；在历史中携带同一调用则可折叠。没有可靠调用 ID 时仍需要明确的历史序列关系。
6. 压缩摘要、被改写的系统提示、变更的参数或工具结果全部展开。远端 `previous_response_id` 等引用只比较引用条目，不拉取或补造其正文。

首版不把“上一条响应中出现过”直接等同于“前面的请求已有”。响应首次进入请求历史时默认展开；响应与请求的检测阶段也不同，后续若扩展跨阶段复用，需要独立验证规则与关联语义。

普通子 agent 可以从独立任务启动，fork 子 agent 可以继承完整父上下文；恢复已有 agent 则继续自己的历史。压缩、side 转为具备工具能力的 fork、同名 agent 新实例等行为分别处理，不以名称或共享目录判定上下文相同。网关未观察到的 compact 请求或客户端事件不补造，具体机制和验证边界见补充调研。

## 4. 风险检测复用

### 4.1 缓存内容与有效条件

缓存的是一个完整检测单元在确定条件下的结论，不是上一条请求的整份 `findings`。

检测单元以可独立检查的完整条目为边界；单位内的长字符串窗口、嵌套参数及多条规则必须处理完后，才能提交可复用结果。首次支持已知结构的文本、工具调用与工具结果；未知结构或不能明确划定检查范围的内容按现有流程完整检测。

复用键至少包含：

```text
会话归组及配置入口 / 协议
+ 指纹格式版本 / 完整条目指纹
+ 角色、工具类型与名称、检测阶段、继承的敏感字段上下文
+ 规则与参数解析器版本
+ 有效凭据集合、本地规则凭据子集的独立摘要及完整性状态
```

有效凭据集合覆盖本地已知密钥，以及现有流程从请求、响应头和正文学习到的凭据。本地规则使用的凭据子集也单独参与依赖：即使新旧密钥已同时被学习，换钥后合并目录不变，也需要重新检查。缓存保存摘要，不额外保存凭据明文。首版采用整个有效集合的保守失效策略；集合变化时重新检查相关单元，不假设旧的“没有命中”仍然成立。

缓存身份与上下文身份分开：同归组的主线程、明确 fork 或 side 回放，若完整单元及实际检查依赖相同，可以共享计算模板。不同上下文仍保留各自的请求、证据及出现身份；缓存命中不证明它们是同一次历史事件。未来规则若依赖整段对话，必须增加其上下文依赖或禁用该规则的单元复用。

结果包括规则命中模板、条目内的结构定位、敏感位置标记、实际覆盖范围、覆盖限制和检查版本。没有命中的完整结果也必须缓存，否则常见的普通历史仍会重复检测。

结果的可复用性按检测单元判断，不直接使用整条请求的 `inspectionStatus`：例如响应包含图片导致整体 `limited`，不妨碍已完成的请求文本单元复用。已知的能力限制继续继承；处理失败、预算不足、解析缺口或没有确认完整检查范围的结果，不能作为“已检查完”来跳过检测。

### 4.2 后台处理流程

1. 继续接收、暂存与转发完整原请求。
2. 在已有的后台结构读取、凭据学习流程中建立完整条目指纹、会话归组和上下文元数据，完成检测依赖确认。
3. 查询兼容且已提交的检测结果；命中时复用，未命中、版本改变或上下文失效时检查该单元。
4. 继续保存当前请求的完整正文；复用单元的敏感标记和风险引用按当前序列及正文位置重建。
5. 将当前记录的结果、复用来源及检测进度提交。单元缓存仅在对应结果已成功持久化后可供后续任务使用。

请求内容在命中缓存后仍需要接收、结构读取、哈希和保存，减少的是重复规则匹配及工具语义检查。首版不承诺网络、磁盘或总处理时间按历史比例等比例下降，实施后需要实测这些开销。

如果前一请求仍在检测，后来的请求只使用已经完成并持久化的单元结果；其余照常检查，不等待前一请求或阻塞转发。首版允许这种并发下的少量重复工作，不新增按会话串行排队。

### 4.3 证据与新事件

- 复用结果仍关联到当前请求，并标注“复用第 N 条请求的检查结果”和原检查时间。
- 当前请求的 `requestId`、结构路径、字节偏移及工具证据快照重新生成或绑定。证据不能依赖上一条记录的偏移；上一条被清理后，当前记录仍可以独立复核。
- 本轮响应和新提出的工具调用继续按现有流程检测；流式增量与中间证据不直接参与首版请求历史复用。
- “内容检测计算可复用”与“发生了同一个事件”分开判断。一个新的调用即使能命中兼容检测模板，也仍是新事件，保留自己的风险发现与未知执行状态。
- 历史内容被折叠但尚未检查完成时，仍显示待检查或不完整；不能用折叠状态代替检查结论。

### 4.4 展示与统计口径

为避免仅减少计算、页面却继续反复展示同样风险，建议同时区分历史携带与新增出现：

| 场景 | 当前请求 | 会话累计 |
| --- | --- | --- |
| 旧的风险条目再次作为历史携带，结论不变 | 保留关联，放入“历史风险”折叠组 | 不再作为新增发现累加 |
| 相同命令出现新的调用 ID 或明确的新位置 | 保留新的风险发现 | 计入新增发现 |
| 历史条目因规则或凭据变化产生新命中或不同结论 | 显示新增或更新的检测结论及原因 | 记录新的结论版本，不把变化隐藏在旧结果中 |
| 缓存复用但条目属于明确的新事件 | 标注检查复用，同时显示新增风险 | 计入新增发现 |

现有 `findingCount` 和最高严重程度继续描述每条请求的全部关联风险，`hasRisk` 和分类筛选仍能找到携带历史风险的记录。新增“新增风险 / 历史风险”字段供页面显示；会话主要显示新增发现数，并将全部请求中的风险关联次数单独标明，不混用两个数量。

因此，风险的出现身份需要独立于检测缓存键：前者由可靠历史条目关联确定，后者只决定是否重新计算。历史来源、首次出现和结论版本作为轻量元数据保存，不能只用正文哈希给所有相同操作去重。上下文或出现身份有歧义时，保留独立风险关联，不宣称已经完成历史事件去重。

## 5. 数据、兼容与性能

建议新增共享的条目索引与历史匹配模块，供展示和后台检测调用，避免两套解析边界逐渐不同。

- 每条请求保存会话归组、可识别上下文及继承关系，和轻量条目元数据：原序号、类型、角色、源范围、完整指纹、历史来源与出现身份。索引关联 manifest，正文清单变化时失效。
- SQLite 增加可复用检测结果及单元关联数据，缓存与已有审计保留周期和容量预算共同管理；版本升级使用事务迁移。
- 当前请求的完整正文、风险和必要证据独立留存。历史来源链接可以因清理失效，当前内容和结果不会变成无法展开的引用。
- 读取新增视图返回有序的显示节点：历史区间摘要或新增条目，按显示节点分页。历史正文展开继续按原条目分页读取，原索引保持稳定。
- 现有 `/content?offset=...` 完整条目接口保留，新增视图使用独立参数或接口；详情与风险导航明确选择对应读取方式，不改变旧 offset 的含义。
- 保持列表轻量、正文按范围读取、内容解析与审计写入隔离。缓存和候选匹配有明确预算，耗尽时回退检测或完整展示，并保留真实的检查失败状态。

已有记录可从完整留存正文按需建立展示索引，不重新发送请求，也不改写原正文。旧记录的风险发现通常没有单元级“检查完成且没有其他命中”的证明，因此不直接作为可信的阴性缓存；首版保留旧检测结果，新的请求首次建立检测单元结果后再供复用。

旧记录缺少历史身份时不追溯伪造去重关系。统计应明确区分旧口径记录与新索引覆盖的记录，避免上线后无解释地减少既有发现数。

内容结构解析完整性、正文留存完整性和风险语义覆盖继续分别展示。包含完整图片载荷不表示已检查图像语义；缓存命中也不把已有能力限制升级为“安全”。

## 6. 实施顺序与验收

确认后按三个步骤实施并逐步验证：

1. 区分会话归组、thread / agent 上下文与明确的继承关系，建立共用条目指纹、历史来源与有界匹配，增加索引存储和兼容读取。
2. 完成默认折叠、新增视图分页、全部展开及风险与原文导航。
3. 增加单元检测缓存、凭据与版本失效、当前证据重绑定，以及新增 / 历史风险展示与统计。

关键验收场景：

- Codex 与 Claude 的长会话不断追加历史，默认可直接看到新增内容，全部展开后与当前记录的原始次序一致。
- 历史跨越多个分页、历史与新增交错、整份重试、空输入、只有工具结果、没有可靠会话标识。
- 两次相同用户文字，以及不同 ID 的相同工具调用，不能误当作同一历史事件。
- Codex 主线程与临时 fork 共享会话头、Claude 主请求与 side 交错；历史前驱不串线。普通子 agent、fork、恢复与同名新实例分别处理，身份不足时保留未知。
- 历史被裁剪、压缩、插入、系统提示变化、字段顺序变化、内容块角色变化与歧义重复，正确展开或保守回退。
- 超长文本、中文和 emoji、转义字符串、结构化参数及内嵌 JSON，复用后风险仍定位当前请求的准确位置。
- 已完成且没有风险的单元命中缓存；规则、解析器或有效凭据集合变化后重新检测。
- 前一检测未完成、单元失败、资源不足、旧正文缺失或中断时，不错误标记已完成。
- 重启和旧记录升级、来源过期清理、缓存淘汰后，当前记录仍可独立查看；回退行为可验证。
- 新事件与历史携带分开计数，新增结论保持可见，风险筛选和最高严重程度不丢失。
- 以相同请求序列比较开启复用前后的规则执行次数、检查字节、CPU 时间、详情延迟及存储开销；不只以页面折叠或总耗时判断成功。

建议确认的首版范围：基于现有 HTTP 信号区分会话归组与上下文、处理明确的继承关系、同上下文及可确认继承历史的折叠、新增内容优先读取、同归组已完成检测单元复用、当前证据定位，以及新增与历史风险区分。正文存储去重、无关会话间的缓存共享、响应到请求的跨阶段复用、compact endpoint 接入和 hooks / 本地 transcript 等额外客户端集成不纳入首版。

## 7. 首版实现说明

- 共用现有请求投影建立结构指纹与历史身份；`/content?view=folded` 按显示节点分页，`view=all` 保留原条目 offset。详情默认折叠，历史展开从当前请求读取。
- 完整条目指纹约束其内部规则检查模板的复用。请求完整解析、正文和发现成功持久化后才提交缓存；解析、凭据学习、敏感标记及当前工具证据生成继续使用原流程。
- 风险结论身份独立于计算缓存。缓存淘汰后的重新检查不把相同历史结论计为新增；凭据或规则改变后的新结论保持可见。
- 请求行与轨迹导航分别标识未发现风险、存在新增风险和仅含历史风险；新增与历史并存时展示各自数量。
- 新收到的完整请求建立持久索引。旧记录继续提供完整内容查看，首版不自动回填历史关系或阴性检测证明，也不修改旧统计。
