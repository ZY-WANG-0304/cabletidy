# CableTidy 0.4.0-rc.6

这是 `0.4.0` 的第六个候选版本，基于合入 [PR #51](https://github.com/ZY-WANG-0304/cabletidy/pull/51) 至 [PR #55](https://github.com/ZY-WANG-0304/cabletidy/pull/55) 后的 `origin/main`（`34e5932`）。以下汇总相对 `0.4.0-rc.5` 的变化；之前的功能见 [0.4.0-rc.5 发布说明](0.4.0-rc.5.md)。候选包发布到 npm `next`，`latest` 保持稳定版 `0.3.0`。

## 新增与修复

- “配置套装”更名为“线路”（英文 Cable），管理台、CLI 和管理接口统一使用新名称。`config.json` 从版本 `2` 升到 `3`，`bindings` 更名为 `cables`；旧配置加载时自动转换，保留线路 ID、上游凭据和模型设置。升级前已应用的 Claude Code 接管记录仍可读取和撤销。当前每条线路仍只连接一个上游。见 [PR #53](https://github.com/ZY-WANG-0304/cabletidy/pull/53)。
- 线路导入与导出改为独立页面，支持返回、浏览器前进 / 后退及未保存修改保护；长名称不会撑出页面。导入继续先预览，再明确选择更新已有线路或创建新线路。见 [PR #52](https://github.com/ZY-WANG-0304/cabletidy/pull/52)。
- 默认审计存储上限由 128 MiB 提高到 5 GiB（5120 MiB），仍默认保留 30 天；两项均可单独选择“不限”。新建配置或缺少上限字段时使用新默认值，已保存的上限和“不限”保持原值。容量按需使用，不会预占 5 GiB。见 [PR #51](https://github.com/ZY-WANG-0304/cabletidy/pull/51)。
- Claude Code 接管字段被外部修改后，应用或撤销会提示冲突字段，取消时保留当前文件，确认后先备份再继续。重新应用后的撤销仍恢复最初接入前的值；覆盖前的外部修改可从备份找回。确认不显示秘密值，客户端文件再次冲突或线路相关配置改变时旧确认失效，需要重新确认或刷新后重试。无效 JSON、非普通文件和符号链接仍拒绝覆盖。见 [PR #54](https://github.com/ZY-WANG-0304/cabletidy/pull/54)。
- 审计维护被文件锁暂时阻塞时延后维护，不再使可正常读取的审计记录返回 `503` 或丢弃健康连接；解除锁后恢复维护。该修复随 PR #53 合入。
- 生成 Codex 配置时在 provider 分隔注释前增加空行，使原有配置与 CableTidy 管理块更易区分。见 [PR #55](https://github.com/ZY-WANG-0304/cabletidy/pull/55)。

## 管理接口与文件兼容性

- 导出接口由 `POST /api/v1/config/export` 改为 `POST /api/v1/cables/export`，选择字段由 `bindingIds` 改为 `cableIds`；导入接口由 `POST /api/v1/config/import` 改为 `POST /api/v1/cables/import`。其他管理请求中的 `bindingId` 同步改为 `cableId`，`status` 的线路列表字段为 `cables`。旧请求字段返回 `422 renamed_request_field`，外部脚本必须更新，不能依赖旧字段被忽略或自动选择默认线路。
- 新导出文件标识为 `cabletidy.cables`，文件版本仍为 `1`，内部配置版本为 `3`。旧 `cabletidy.configuration-suites` 文件（内部版本 `2`）仍可导入；同时包含 `bindings` 和 `cables` 的文件拒绝导入，不部分写入。新版配置或导出文件不保证能被旧版 CableTidy 读取。
- 服务设置继续保存于 `config.json` 的 `audit` 字段，不随线路导入导出。导出默认不含凭据，移除上游 URL 中的用户名、密码、查询参数和片段；依赖查询参数的地址需在导入后补齐。含凭据的导出文件包含明文秘密，应按敏感数据保管。导入不会自动修改客户端文件。

## 安装要求

- 支持 Node.js `^22.13.0 || >=24`，推荐 Node.js 24。npm 包自带原生程序，没有 npm 运行时依赖，安装不需要 Rust，也不下载额外二进制。
- 完整发行包包含 Linux x64 / arm64（musl）、macOS x64 / arm64 和 Windows x64。源码构建需要 Rust 1.95 或更新版本及系统 C 工具链。
- Codex 可选模型设置依赖本机支持 `debug models --bundled` 的 Codex CLI；纯透传不依赖该目录。Windows 的模型目录查询需要允许 `Add-Type` 的系统 Windows PowerShell。

## 安装与升级

1. 用旧版 `cabletidy stop` 停止服务，确认退出后备份完整 CableTidy 数据目录（默认 `~/.cabletidy`）及 Codex / Claude 配置目录。
2. `0.4.0` 候选版审计数据库保留敏感原文，可能包含认证信息、对话及工具内容；备份和含凭据的导出文件应按敏感数据保管。旧版已脱敏记录不会恢复为原文。
3. 确认 npm 已发布候选包后安装并启动：

```bash
npm view cabletidy@0.4.0-rc.6 version --registry=https://registry.npmjs.org/
npm install -g cabletidy@0.4.0-rc.6 --registry=https://registry.npmjs.org/
cabletidy --version
cabletidy start
cabletidy status
```

也可从 [GitHub Pre-release](https://github.com/ZY-WANG-0304/cabletidy/releases/tag/v0.4.0-rc.6) 下载 `package.tgz`、`SHA256SUMS` 和 `release.json`，核对摘要及来源后执行 `npm install -g /absolute/path/package.tgz`。GitHub Release 与 npm 独立发布，是否可从 npm 安装以 registry 查询结果为准。

从 `0.4.0-rc.5`、更早的 `0.4.0` 候选版或 `0.3.0` 升级继续沿用 `config.json`、`secrets.json` 及已有审计数据库。旧 `bindings` 自动读取为 `cables`，后续保存使用配置版本 `3` 和新字段；同时包含新旧字段的配置需先修正，避免歧义。无需因名称变化重新应用已接入的客户端；线路 ID 和本地 URL 保持不变，重命名线路时仍需重新应用。若希望已有配置使用更大的审计上限，请在“设置”中改为 5120 MiB 并保存。

外部管理脚本需按上节更新接口路径和字段；启动后核对已有线路、模型映射、客户端接管状态、审计记录及服务设置。Codex 的注释空行在下次主动应用配置时更新，daemon 启动不会改写客户端文件。Claude Code 配置冲突确认覆盖的是接管字段，确认前应核对预览及备份路径，应用后重启 Claude Code。

从 `0.2.0` 或早期 `0.3.0` 候选版升级时，还需遵循 [0.3.0 发布说明](0.3.0.md) 中的停止服务、旧目录锁迁移及客户端配置步骤。不要删除或替换新版持久的普通 `daemon.lock` 文件。

已支持 `update` 的版本可执行 `cabletidy update 0.4.0-rc.6`，按提示重启服务。`cabletidy update next --check` 检查后续候选版，`cabletidy update next` 安装；无参数的 `update` 使用稳定版 `latest`，当前候选版高于稳定版时不会自动降级。非交互终端默认拒绝启停确认，自动更新并重启需显式传入 `--yes`。

## 已知限制与恢复

- 安全审计仍为“仅记录”，不阻断操作，不额外调用模型，也不确认工具真实执行结果。无风险发现、检查复用或“已检查”均不表示已证明安全；会话与上下文标识来自客户端，无法可靠匹配的历史保守展开。
- 每条请求继续独立保存完整正文，不做正文存储去重、无关会话之间的缓存共享或响应到请求的跨阶段复用；旧记录不补造历史关联或阴性缓存。
- 存储上限是审计容量预算，仍在处理的记录或读事务占用的 WAL 会延后回收，磁盘占用可能暂时超出上限；为写入状态和风险信息保留空间后，实际留存量可能低于上限。两项均不限时应自行监控磁盘。数据库或队列不可用时代理继续工作，页面显示检查失败、覆盖有限或存储缺口；设置不会恢复已经清理的记录。
- 数据目录应位于本地文件系统，不承诺 NFS / SMB 或跨机器共享锁协调；不包含开机自启或崩溃自动重启。原生程序独立运行时需手动替换二进制，`update` 仅适用于全局 npm 安装。
- 恢复旧版前先停止候选版并确认退出，保留当前数据副本，再安装旧版本并恢复升级前的数据及客户端配置备份。不要直接让旧版读取已迁移至版本 `3` 的配置代替恢复演练，也不要同时运行新旧 daemon。

## 发布与验收

发布提交需通过版本一致性、格式、严格 Clippy、Rust / JavaScript 测试及安装冒烟验证。`v0.4.0-rc.6` 的 tag 工作流执行 Linux、macOS、Windows × Node.js 22.13.0 / 24 六组检查、五平台构建和最终完整包安装验证；以该 tag 的成功运行及 `release.json` 记录的提交、ref、运行 ID 和摘要为产物依据。

GitHub Pre-release 在工作流成功后自动创建并附上完整包、摘要和提交信息；npm 使用同一份已验证的 tarball 发布到 `next`。发布后核对 registry integrity 与标签，并使用隔离缓存和数据目录验证安装、版本、管理台、停止及重启。

本候选版的真实 Codex / Claude 上游接入、旧版升级与恢复、长期审计留存与磁盘压力、长会话及 fork / side 历史匹配，以及 Windows 真实终端 Ctrl+C 与交互更新仍需人工验收；自动化模拟测试及此前版本的人工结果不能替代本候选版验收。完整范围见 [维护者发布流程](../release-process.md)。
