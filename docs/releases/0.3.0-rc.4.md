# CableTidy 0.3.0-rc.4

这是 `0.3.0` 的第四个候选版本，基于合入 [PR #24](https://github.com/ZY-WANG-0304/cabletidy/pull/24) 后的 `origin/main`（`4576226`），重点修复主机名变化后无法停止 daemon 的问题。上一候选版本的模型配置、上游代理和安全审计改进见 [0.3.0-rc.3 发布说明](0.3.0-rc.3.md)。

## 新增与修复

- 使用操作系统独占文件锁保证同一数据目录仅运行一个实例，替换目录锁、心跳和过期回收。异常退出后由操作系统释放锁，无需等待旧版的 10 秒心跳过期。
- `stop` 和 `status` 通过本地控制通道连接实际实例：macOS / Linux 使用 Unix domain socket，Windows 使用仅当前用户可访问、拒绝远程连接的 named pipe。协议版本与实例 UUID 用于核对目标，主机名、PID 和进程启动时间仅供诊断。
- 停止仍等待请求排空、持久化和清理完成；控制连接提前断开会报告未确认正常退出，不会误报成功。状态查询区分运行中、排空中、持锁但无响应和未运行。
- 取消 `stop` 客户端等待会释放控制连接名额，但不撤销已接受的停止请求。修复反复取消等待耗尽 32 个连接名额、导致后续状态查询和停止连接超时的问题。
- 遇到旧版目录锁时返回 `ELOCKLEGACY` 并提示人工迁移，不自动控制旧 daemon 或回收旧锁。

## 安装与升级

支持 Node.js `^22.13.0 || >=24`，推荐 Node.js 24。计划提供 Linux x64 / arm64（musl）、macOS x64 / arm64 和 Windows x64 五平台完整安装包；安装不需要 Rust，源码构建需要 Rust 1.95 或更新版本。

升级前备份完整 CableTidy 数据目录及 Codex / Claude 配置目录，并停止旧服务。先尝试旧版的 `cabletidy stop`；如果旧版因主机名变化而拒绝停止，从 `runtime.json` 读取 PID，使用系统进程工具核对后手动执行 `kill <实际 PID>`，Windows 使用 `taskkill /PID <实际 PID>`。占位符须替换为已核对的数字。从 `0.2.0` 升级时，在原终端按 Ctrl+C 或通过原进程管理器停止旧服务。

确认旧进程已退出后，如果数据目录中仍有旧版的 `daemon.lock` **目录**，手动删除这个目录，再启动新版。新版不会自动回收旧目录锁，即使其中的 PID 已失效。保留 `config.json`、`secrets.json` 和审计数据。

新版的 `daemon.lock` 是持久的**普通文件**，退出后保留；文件存在不代表实例仍在运行，不要删除或替换它。不能仅凭 `status` 无响应就清理锁，暂停或正在排空的实例仍可能持有锁。

确认 npm 已发布本版本后执行：

```bash
npm install -g cabletidy@0.3.0-rc.4 --registry=https://registry.npmjs.org/
cabletidy --version
cabletidy start
cabletidy status
```

npm 尚未发布时，可在 GitHub Pre-release 创建后下载 `package.tgz`、`SHA256SUMS` 和 `release.json`，核对摘要与来源，再用 `npm install -g /absolute/path/package.tgz` 安装。此次生命周期改动不要求重新应用已有客户端配置；从更早版本升级时仍需遵循对应版本的数据迁移说明。

回退前先用新版 `stop` 停止服务并确认退出，保留当前数据副本，再安装旧版本并恢复升级前的数据与客户端配置备份。新旧版本的锁协议不同，不要让旧版直接使用含新版普通锁文件的数据目录，也不要同时运行新旧 daemon。

本版本处于发布准备阶段，尚未创建 `v0.3.0-rc.4` tag，未发布 GitHub Pre-release 或 npm 包。

生命周期实现提交 `f31e04b` 已通过 Linux、macOS、Windows 与 Node.js 22.13.0 / 24 的六组 CI，包含完整测试与发行包安装、启停、重启和卸载验证。该结果验证的是发布前的实现提交；`0.3.0-rc.4` 的跨平台发行验证以新版本对应提交的 Actions 为准。

计划 tag 为 `v0.3.0-rc.4`。tag 工作流通过完整测试矩阵、五平台构建及安装验证后，会创建 Pre-release 并附上完整安装包、摘要与提交信息。npm 发布是独立步骤，候选版进入 `next`，不改变稳定版 `latest`；GitHub Release 创建成功不代表 npm 已发布。

数据目录应位于本地文件系统，不承诺 NFS / SMB 或跨机器共享目录的锁协调；不包含开机自启或崩溃自动重启。安全审计仍为仅记录模式。真实 Codex / Claude 上游接入、旧版升级与恢复演练，以及 Windows 真实终端 Ctrl+C 的事件投递仍需人工验收，自动化测试不能替代这些验证。完整清单见 [维护者发布流程](../release-process.md)。
